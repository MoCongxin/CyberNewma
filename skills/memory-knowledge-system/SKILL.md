# 记忆知识体系（Memory & Knowledge System）

## 一句话定位

执行中产生的经验（踩坑 / 反直觉行为 / 决策反转）**立即**沉淀为结构化 memory 条目，每条必含根因与复用指引；索引同步更新是沉淀动作的一部分。memory 是 agent 跨 session、跨任务的长期记忆——**不被索引的条目等于不存在**。

## 目录结构

```text
docs/
  specs/            # 需求域工件（目标谓词、判定条件）—— 不是 memory
  archs/            # 设计域工件（决策与演化链）—— 不是 memory
  memory/
    MEMORY.md       # 总索引（唯一入口）
    feedback/       # 踩坑记录（单点症状 + 根因 + 规避）
    guide/          # 工程指南（可重复执行的方法 + 红线）
    design/         # 设计决策沉淀层：accepted arch 的"当前状态"浓缩（见下）
    ontology/       # 领域本体（可选，元语言层）
    project/        # 进行中工作的进度备忘
    reference/      # 外部资源索引
```

**memory 与流程工件的区别**（避免混淆，这是三个不同的顶层目录）：

| 目录 | 是什么 | 谁写 | 时效 |
|---|---|---|---|
| `specs/` | 需求工件：要解决什么问题、判定条件是什么（有状态机、可被 arch 引用） | 需求域 | 随 spec 状态演化 |
| `archs/` | 设计工件：决策与完整演化链（含 superseded 历史） | 设计域 | 长期，走 supersede 链 |
| `memory/design/` | **知识浓缩层**：把 accepted 的 arch 汇总成"当前状态"（无 lifecycle 字段、无演化史） | 任意 agent（由 arch accepted 触发） | 随 arch accepted 刷新 |

> **注意**：`memory/design/` 的 "design" 是**知识层次**的命名（与 feedback/guide 并列），**不是设计域本身，也不是需求 spec**。它只反映当前 accepted 状态，历史演化一律回 `archs/` 查。

所有条目存放在**唯一权威目录**；需要引用时链接，不复制（防双写漂移）。

## 分类判定（先问"输出会被谁引用？"）

| 类型 | 触发问题 | 输出形态 | 时效 |
|---|---|---|---|
| **feedback** | "我刚才踩了什么坑？" | 症状 + 根因 + 规避 | 永久 |
| **guide** | "这类工程任务怎么做？" | 步骤 + 红线 | 长期 |
| **design** | "我们当前的设计决策是什么？" | accepted arch 的浓缩汇总 | 随 arch 演化 |
| **ontology** | "这个领域的元语言是什么？" | 概念模型 + 不变量 | 极长期 |
| **project** | "进行中的工作到哪了？" | 进度 + 关键悬念 | 短期 |
| **reference** | "外部权威资源在哪？" | 链接 + 用途 | 中期 |

判定规则：被**下次类似问题**引用 → feedback；被**多个任务**引用的方法 → guide；被**后续任务**引用的实施蓝图 → design（通常由 arch 汇总而来）；被**多个 design** 引用的元模型 → ontology。

> **本表是分类判定的唯一权威**：其他技能（如 research-methodology）需要判断沉淀归类时回指此处、不复述；分类判定变更时全量检索同步。

## 操作手册：沉淀一个条目（分步）

### 步骤 0：触发判定（发现即做，不攒批）

**动作**：遇到以下任一，**立即**进入沉淀流程：
- 可复用的工程经验（后人还会在同类场景遇到）；
- 反直觉行为（文档说的与实际不符、API 行为出乎意料、隐式契约）；
- 决策反转（推翻既有技术决策——注意：**反转本身要满足与原决策同级的客观验证标准**，"原代码从未存在"是流程理由，不构成技术依据）。

**产出**：无（确认要沉淀）。
**自检点**：我是"现在就知道该写什么"，还是"等 phase 结束再回想"？后者 → 现在写，记忆会失真、攒批必然漏。

### 步骤 1：验证根因（不许写"改了就好了"）

**动作**：在写之前先把根因挖到机制层——用一个能**复现/推翻**自己的动作验证假设（隔离变量、最小复现、读实现源码）。
**产出**：一句机制层解释（不是"这样就好了"，而是"因为 X 机制，所以在 Y 条件下必然出现 Z"）。
**自检点**：我的根因能**预测**下一个同类现象吗？能 → 到机制层了；不能 → 还是症状描述，继续挖。

### 步骤 2：选类与定文件

**动作**：按上文分类判定表选类型，定文件名：
- feedback：`feedback/feedback-<topic>.md`
- guide：`guide/<topic>.md`
- 其他类型按目录语义命名。

**产出**：类型 + 路径。
**自检点**：这个内容真的属于 memory 吗？——若它是**需求判定条件**，应进 `specs/`；若是**设计决策**，应进 `archs/`；若是"当前设计状态汇总"，才进 `memory/design/`。选错目录是本体系最常见的污染源。

### 步骤 3：写条目

**动作**：按 §feedback 条目规范（或对应类型的格式）填写。
**产出**：条目文件。
**自检点**：description 含结论吗？时效锚点（版本号 / 截至日期）写了吗？涉及行号的引用是否声明了时效？

### 步骤 4：同步索引（沉淀动作的一部分）

**动作**：在 `MEMORY.md` 对应分区追加一行，含**蒸馏结论**。
**产出**：索引行。
**自检点**：**扫这一行我就能决定要不要点开吗**？不能 → 蒸馏不足，重写。

## feedback 条目规范（体系核心）

**文件**：`feedback/feedback-<topic>.md`

```markdown
---
name: <一句话结论式标题>
description: <症状 + 根因 + 规避，含关键量化事实>
---

## 症状           # 现象与复现条件
## 根因           # 深挖到机制层，不是"改了就好了"
## 解决           # 具体修复/规避步骤
## Why            # 为什么会这样（机制解释，可迁移）
## How to apply   # 下次遇到类似场景怎么办
```

**红线**：

- 只写结论不写根因 = 不合格
- description 必须含结论（"X 恒为 Y（勿再 ×1000）"式，不是"关于 X 的问题"）
- 涉及版本 / 行号 / 依赖必须注明时效锚点（版本号或"截至 YYYY-MM-DD"）

## guide 条目规范

**文件**：`guide/<topic>.md`，结构：frontmatter + 步骤 + 红线 + Why / How to apply。

**与 feedback 的边界**：单点坑（一次性症状）→ feedback；可重复执行的成套方法（构建陷阱集、测试模式、性能手法）→ guide。拿不准时问"这是一次性的还是成套的"。

## 条目通用纪律

1. **即时沉淀**：发现即写，不攒到 phase 结束——记忆会失真，攒批必然漏
2. **索引同步**：每新增条目必在 `MEMORY.md` 对应分区追加一行；写完自检复核
3. **索引行含蒸馏结论**：一行内给出关键结论 / 数字 / 触发条件，让读者**扫索引即可决策是否点开**
4. **单一权威位置**：每条知识只存一份，引用走链接
5. **定期复审**：project 类随 phase 归档更新；design 类随 arch accepted 触发；含时效锚点的条目半年复核

## MEMORY.md 索引格式

按类型分区（`## Feedback` / `## Guide` / `## Design` / …），每行：

```text
- [条目标题](相对路径) — 一句话蒸馏结论（含关键事实）
```

反例：`- [某坑](feedback/xxx.md) — 踩坑记录`（无信息量）
正例：`- [某库单位恒为米](feedback/xxx-unit.md) — 输出恒为米勿再 ×1000；location 字段只写用户输入，未传入为 NULL`

## 反模式

| 反模式 | 症状 | 修正 |
|--------|------|------|
| **攒批沉淀** | phase 结束才补写 feedback，细节丢失 | 发现即写 |
| **无根因** | 只有"改了 X 就好了" | 挖到机制层再写 |
| **索引漏更** | 条目存在但 MEMORY.md 无对应行 | 沉淀动作必含索引行 |
| **复制粘贴** | 同一知识出现在两处并各自演化 | 链接代替复制 |
| **分类混淆** | 系统调研写进 feedback / 单点坑写进 guide | 用"被谁引用"判定 |
| **目录污染** | 把需求判定条件写进 memory、把设计决策写进 memory（应进 specs/ 或 archs/） | 按"specs=要解决什么 / archs=怎么构成 / memory=经验与浓缩"三分 |
| **描述无结论** | description 只写"关于 X" | 写成结论式（症状+根因+规避） |
| **memory/design 当演化史用** | 在 memory/design 里记录被取代的旧决策 | 演化史归 archs/（supersede 链），design 只反映当前 accepted 状态 |

## Why

执行期经验是协作中最容易蒸发的资产——session 结束即失忆。即时沉淀 + 索引蒸馏让任何后续 session 扫一眼索引就能避免重蹈覆辙；根因层的 Why / How 让经验可迁移，而不是只解当前这个坑。目录三分（specs / archs / memory）的理由是**时效语义不同**：需求与设计决策有生命周期与状态机，经验没有——混在一起会让"当前状态"与"历史演化"无法区分，最终谁都不确定该信哪一份。

## How to apply

遇到触发条件立即按 §操作手册 四步执行（触发判定 → 验证根因 → 选类定文件 → 写条目并同步索引）；phase 归档时复核本 phase 踩坑是否全部入册；定期核对索引与目录一致（有条目无索引行 = 补行；有索引行无文件 = 勘误）。

## 相关技能

- **domain-design**：arch 状态机与 `memory/design/` 沉淀层的触发关系（arch 进 accepted 时提示更新）。
- **domain-demand**：`specs/` 工件规范（与 memory 是不同目录、不同语义）。
- **domain-implement**：债务登记（台账与 memory 的分工——债务有到期与偿还语义，属流程工件；经验属 memory）。
- **本技能属于「人-Agent 协作工作流技能集」**，总览见 workflow-principles，判定依据见 domain-model。
