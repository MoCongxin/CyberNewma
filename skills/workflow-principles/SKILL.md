# 工作流核心原则与技能集总览（Workflow Principles）

## 一句话定位

本技能是技能集的**总览与原则层**：定义贯穿全部技能的七项核心原则（执行纪律层）与文档工件生命周期，并在新项目引入时提供定制清单。**职责语义层（六域判定依据）独立成 domain-model 技能**；**运行时（按域派发）独立成 dispatcher-orchestration 技能**。

**按域组织的形态**：每个核心域一个技能（= 该域子代理的操作手册，由调度者派发时装入）；主 Agent 作为调度者与决策者按性质缺口驱动推进；审核域是独立子代理；验收域职责由调度者承担（子代理是叶子节点）。技能集已剥离具体项目、仓库与技术栈绑定，适用于任何"人 + Agent 协作"的任务形态。

## 单点真相分工（本技能集内部的权威划分）

| 内容 | 唯一权威位置 |
|---|---|
| 七项执行纪律原则、工件生命周期、引入定制清单 | **本技能** |
| 跨域裁决条款（G1–G25、Done 公式、Publisher 不变量、任务树、四层结构、审查义务与审核强度、易混词）与各域对照表 | **domain-model** |
| 运行时（派发循环、派发契约模板、闭合裁决、集成归档） | **dispatcher-orchestration** |
| 域内条款（各域公理、操作手册、工件规范、红线、回报格式） | **各域技能**（domain-demand / design / plan / implement / review、research-methodology） |
| memory 分类与沉淀纪律 | **memory-knowledge-system** |

**规则**：任何条款只在一处成文，其余位置回指不复述。域技能为保持子代理自足，可复述**本域那一行**的停止/交接/失败处理；跨域对照表只在 domain-model。

## 全景：文档工件生命周期

```text
research（调研：带结论的可引用知识；调研型任务自身走六域循环）
   ↓ 启发 / 依据（可为任意域做侦察输入）
report（汇报：讲清楚）
spec（需求：要解决什么问题，判定条件是什么〔需求域〕）
   ↓ 硬依赖：spec 必须 accepted
arch（设计：怎么构成 / 什么结构能保证〔设计域〕）
   ↓ 硬依赖：arch 必须 accepted
plan / task（计划→实施：怎么做、依赖怎么排、门禁是什么）
   ↓ 执行期沉淀                        ↓ 归档反查〔审核域 → 验收域：人类确认闭合〕
memory feedback / guide（踩坑与经验）↔ design / ontology（知识浓缩层）
```

- **research → spec/arch**：research 只列启发不下结论；需求界定落到 spec，最终决策落到 arch
- **spec → arch**：arch 创建时有一条硬前置门控（**条文单点真相在 domain-design 的"接单前置"节**，此处不复述）；一个 spec 可被多个 arch 消费
- **arch → plan**：plan 创建的硬前置门控（**单点真相在 domain-plan 的"接单前置"节**）
- **plan/task → feedback**：执行中踩坑立即沉淀 memory（见 memory-knowledge-system），归档时做 arch 偏差反查
- **arch → memory/design/**：accepted 的 arch 按 scope 定期浓缩为"当前状态"知识层（见 domain-design）

**工件落点速查**：

```text
docs/
  specs/       SPEC.md + NN-<scope>-<topic>.md      # 需求域工件
  archs/       ARCH.md + NN-<scope>-<topic>.md      # 设计域工件
  plans/       PLAN.md + NN-<name>.md               # 计划域工件
  tasks/NN-<name>/  phase-N-*.md, DEBT-REGISTRY.md, archive/
  research/                                         # 调研产物
  reports/YYYYMMDD-<slug>/    init.md + visual.html   # 汇报产物（若启用汇报技能）
  memory/      MEMORY.md + feedback/ guide/ design/ ontology/ project/ reference/
```

### 域路径：性质缺口驱动，不是流水线

域不是任务类型：任务进入哪个域由它当前**缺少的性质**决定（G16），且只进入建立必要性质所需的**最小域集合 D***（G22）——典型路径都是 D* 的结果，不是对全链路做减法。开工前三问：这个任务要建立什么性质（Required）？已经建立了什么（Established）？消除缺口的最小域集合是什么（D*）？

| 典型任务 | 路径 D* |
|---|---|
| 完整工程任务 | 需求 → 设计 → 计划 → 实施 → 审核 → 验收 |
| 独立调研任务 | 需求 → 调研 → 验收（调研是支撑域的独立形态） |
| 简单维护任务 | 需求 → 维护 → 验收 |
| 支撑调研 | 实施 → 调研（supports）→ 实施 |

各域的成立条件、回退与上冒规则，以及支撑域（调研/维护）的双形态语义见 **domain-model**；运行时怎么派发见 **dispatcher-orchestration**。

## 七项核心原则（贯穿所有技能，冲突时以此裁决）

1. **单点真相（Single Source of Truth）**：每类信息只有一个权威位置；其余位置最多保留只读镜像或工作副本，禁止双写。粒度下探到句子：规范句/示例话术只在权威节成文一次，其余位置回指不复述，防句级表述漂移。**技能集内部亦适用**（见上文分工表）
2. **硬门控（Hard Gate）**：层与层之间用可判定的通过条件衔接（命令 + 通过条件 + 不通过则），不允许"目测通过"
3. **文档驱动（Plan First, Execute Next）**：task 文件既是设计稿又是执行记录，先更新设计再写代码
4. **可追溯（Traceability）**：task→commit 走 githash 回链；事实引用走 `file:line` 或 URL；决策演化走 supersede 双向链；需求→设计走 spec↔arch 双向引用
5. **就地标注偏差（Deviation In Place）**：实际实现偏离设计时，不删原图/原文，在旁边加"实施偏差"注记——这是后续追溯的关键证据
6. **不删除历史（Archive, Don't Delete）**：完成的任务移入 `archive/`，被取代的决策标记 `superseded`，演化史永远可还原
7. **债务显式化（Debt Tracking）**：带偿还义务的未终态事项（如临时路径/已知缺口）当场登记（task 债务节 + plan 登记簿），每条带截止与行为验收标准，偿还附证据，归档前终态核销——不允许无到期日期的中间态

七项原则是**执行纪律层**；其上还有一层**职责语义层**——六域模型（见 domain-model）裁决"这个问题归哪个域、该域的成立条件是什么、何时回退/上冒"。两层正交，配合方式：**先按域定位职责边界，再按七项原则裁决规则冲突**。例如"计划期发现设计做不了"，先由域语义给出回退方向（G4：回退设计域，不在计划层偷改），回退过程的落点纪律再由单点真相、不删除历史接管。

## 新项目引入定制清单（引入本技能集时先花 10 分钟定制）

### 谁做、按什么顺序（引入动作必须先有人认领，否则新 agent 会卡在"这活归谁"）

**引入不是任何域的工作**（它发生在任务存在之前），所以它不属于需求域，也不能等某个域子代理顺手做。责任人只有两个：

| 步骤 | 动作 | 责任人 | 产出 |
|---|---|---|---|
| I-1 | 建流程文档骨架：`docs/` 根目录 + 三份索引（`specs/SPEC.md`、`archs/ARCH.md`、`plans/PLAN.md`） | **调度者（主 Agent）执行**；也可由用户手工建 | 空索引文件（含表头与格式说明） |
| I-2 | **判断是否需要项目侧 scope 词表**：框架已有默认表，**默认情况下不需要**；仅当项目要换一套划分或要加表外取值时才做 | 调度者判断；有则与用户确认 | 项目词表（可选） |
| I-3 | 确认流程文档根目录取值、母仓/submodule 配置（若需要） | 用户 | 项目侧配置节 |
| I-4 | 首次路由：按 §域路径 算第一个任务的 `Required(T)` 与 `D*` | 调度者 | `域路径/路由依据` 记录 |

**关键点**：**索引文件必须预先存在**——需求域与设计域的操作手册都以"读 `SPEC.md`/`ARCH.md` 取最大序号"为前提，若骨架不存在，它们只能 Blocked。所以 I-1 必须在第一次派发之前完成。
**注意**：**"框架默认词表 + 项目无自定义词表"下，需求域不会被词表卡住**——直接用默认表即可。只有在你判断"本项目需要一套不同划分"（I-2）却又未经用户确认时才需要等；此时正确动作是**向用户报 Blocked 并附词表草案**，而不是自造一个然后往下推。

- **流程文档根目录**：示例统一使用 `docs/`（流程文档与代码同仓共存），可按团队工具链替换（`.claude/`、`.agent/` 等），全套技能内路径前缀同步替换
- **scope 受控词汇表**（**已有框架默认值，通常什么都不用做**）：arch / spec 的 `scope` 取值默认使用 **domain-model 的「受控词汇（scope）」节**给出的框架默认表（`product` / `architecture` / `data` / `interface` / `middleware` / `tooling` / `security` / `observability` / `process` / `cross-cutting` / `meta`）。**只有当项目需要一套不同划分、或需要增加表外取值时**，才在项目侧声明自己的词表（写入项目 AGENTS.md 或规范文档的同一张表，单点真相）——项目词表优先级高于框架默认表
- **版本登记表 / roadmap**（可选）：arch 的 `version` 字段引用它，不自行发明版本号
- **工具依赖最小化**：设计期图示用 ASCII（任何 viewer 可读），仅归档期类图用 mermaid（需 `mmdc` 验证）；验证 gate 用项目自身的构建/测试命令
- **单仓边界**：全部流程文档集中在项目内单一权威目录（默认 `docs/`）；多仓 / submodule 拆分场景启用**跨仓同步技能**（技能集中若已启用），其母仓路径与 submodule 身份等**项目特有配置写在项目侧配置点**（项目内配置节或 AGENTS.md），不入技能正文
- **术语/规范句变更必配检索清零**：修改定义、术语或规范话术后，收尾动作固定为对旧表述全量检索（rg/grep）；命中点要么同步修改，要么就地注记保留理由并回指权威处。检索零命中的留档即变更回执
- **示例服从条文**：技能中的示例话术、示例命令仅作说明，与规范条文不一致时以条文为准；发现的表述漂移属于债务（定义见 domain-implement）——当场修复不立债，不能当场修复的登记编号并接线偿还点

## 版本与镜像纪律

- **开发权威源**：技能集的唯一权威源是**独立技能仓**（git 管理，跨项目、跨机器，不隶属于任何具体项目或母仓——独立项目与 submodule 项目平等适用）；修订条文一律在权威源 clone 中进行
- **分发副本**：各机器的 `~/.agents/skills/` 以**目录联接**指向权威源 clone，权威仓 `git pull` 后该机所有项目即刻得到最新条文；项目内**不保留** docs/skills 类镜像（历史遗留副本一律冻结退役）
- **缺陷回传**：任何项目使用中发现条文缺陷，回权威源修复后 commit/push，**不就地修改**任何分发或项目侧副本——多项目共享的条文一旦就地改，即对其他项目产生未声明的行为变更
- **项目特有值与通用条文分离**：配置类内容（母仓路径、submodule 名、scope 词汇表取值）永远放项目侧（AGENTS.md 配置节等）；技能正文只承载跨项目不变的流程与纪律

## Why

七项原则是技能集的宪法层：具体技能（plan/task 结构、arch 状态机、spec 章节格式）回答"怎么做"，原则回答"两条规则打架时听谁的"——例如"示例与条文冲突"听单点真相，"实现与设计图不符"听偏差就地标注。把它们独立成技能而非分散进各技能，是因为裁决需求出现在任意技能的执行现场，必须有单一权威位置可回指；同理，新项目引入时的定制项（scope 词汇、文档根目录）不预先定义，后续所有工件都会各自发明一套词汇，演化成无法跨 plan 检索的方言。

**单点真相为什么必须下探到技能集内部**：v1 把六域总表、停止交接表、记号表在 domain-model 和各域技能里各写一遍，短期看"两处都能查到很方便"，长期看两条表述必然漂移，而使用者无法判断哪条是权威。按内容类型分工（跨域裁决在 domain-model、域内条款在域技能、域技能保留本域一行）后，两类读者各自自足，且每句话只有一个权威位置。

## 相关技能

- **domain-model**：判定依据层（跨域裁决条款权威）。
- **dispatcher-orchestration**：运行时（主 Agent 的操作手册）。
- **各域技能**：域内条款权威，含操作手册与工件规范。
