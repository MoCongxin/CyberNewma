# 工作流域模型（六域、支撑域与横切治理）

## 一句话定位

本技能是技能集的**判定依据层（宪法）**，以四个正交维度收束：

> **Core Domain（核心域）+ Support Domain（支撑域）+ Service（服务）+ Governance（治理）**

> **域负责让命题成立，支撑域负责让能力可复用，治理负责让责任闭合；性质缺口决定路径，而不是任务类型。**

## 单点真相分工（读本技能前先知道的边界）

技能集内有两类条款，权威位置不同，**不得互相复述**：

| 条款类型 | 举例 | 唯一权威位置 | 其他技能如何引用 |
|---|---|---|---|
| **跨域裁决条款** | G1–G25、Done 公式、Publisher 不变量、任务树推出表、四层结构、正交性判据、易混词表、上冒判据、审查义务与审核强度、领域注册表 | **本技能** | 回指本技能（域技能自足时不回指，见下） |
| **域内条款** | 各域公理与判定方法、操作手册、工件规范、红线、回报格式 | **各域技能**（domain-demand / domain-design / domain-plan / domain-implement / domain-review / research-methodology / memory-knowledge-system） | 本技能只登记"操作化位置"，不复述内容 |
| **各域停止/交接/失败处理表** | 跨域横向对照（调度者比对用） | **本技能**（§各域停止条件对照表） | 域技能只保留**本域那一行**的完整版，并注明跨域对照见本技能 |
| **运行时的载体与工序** | 性质台账（`established` 的字段与更新时点）、派发契约模板、闭合与归档九步、并行与终止规则 | **dispatcher-orchestration** | 本技能只定义记号与语义，并显式回指（如 `Established` 记号的载体 → dispatcher §2.1） |

**为什么这样切**：域技能必须**自足**（子代理只读一份手册就能干活，不依赖加载本技能）；但同一条规则在两处各写一遍必然漂移。按"内容类型"而非"名分"分层，两类读者各自自足，且每句话只有一个权威位置。

## 域的本体：性质/职责，而不是任务类型或流程阶段

> **域不是任务类型，也不是流程阶段；域表示任务当前需要建立、维护或判断的一类性质/职责。**

因此：Domain ≠ TaskType、Domain ≠ Role、Domain ≠ PipelineStage，且：

```text
Domain(T) = f(Required(T), CurrentState(T))
```

两个输入都与"任务叫什么"无关：Required 来自**契约**（不来自任务名称），CurrentState 来自**任务状态**（不来自执行历史的长短）。因此同一个任务在不同时刻可以处于不同域（性质一旦建立，缺口即消失）；同一个域可以被完全不同类型的任务进入（只要它们缺同一种性质）。

任务不是因为"它属于开发/调研/文档"才进入某个域，而是因为当前**缺少某种性质**，需要某个域来建立这种性质。形式化为**性质建立算子**（`Dᵢ: S(T) → S(T) ∪ Pᵢ`——进入域 i 给任务补上它负责建立的性质）：

| 域 | 建立性质 Pᵢ |
|---|---|
| 需求域 | `{WellDefined}` |
| 设计域 | `{Refined, Invariant}` |
| 计划域 | `{Executable}` |
| 实施域 | `{Realized, Evidenced}` |
| 审核域 | `{Verified}` |
| 验收域 | `{Closed}` |
| 调研（支撑） | `{Evidence, Knowledge}` |
| 维护（支撑） | `{Maintained}` |

**域路由由性质缺口驱动（G16）**。缺口路由的 resolve 语义分四步：① 找出所有 `provides_properties ∩ Gap(T) ≠ ∅` 且 `required_properties ⊆ Established(T)` 的域（性质供给与前置来自领域注册表，见下文）——**审核域除外**（其唯一入选通道为②的义务使能）；② 叠加**审查义务两规则**：存在成熟且未履行的审查义务 ⇒ 审核域入候选（**使能**）；凡 `required_properties` 与义务 subject 相交的域退出候选（**阻塞**，见「审查义务与审核强度」节）；③ 在能覆盖缺口的域中按最小充分条件选出一组（G22）；④ 多个域都能消除同一缺口时，按确定性平局规则（性质依赖序 + 注册序）选择，并**把选择结果显式记录**（写入任务文档），不依赖默认顺序：

```text
Gap(T) = Required(T) − Established(T)
Domain(T) = arg resolve(Gap(T), Obligations(T))    # 审查义务参与候选集过滤
```

> **审核的发生由契约声明的审查义务决定，不由 Gap(T) 决定**：`Verified ∈ Gap` 而无义务 ⇒ 不审查，路径逐字节不变；有成熟义务 ⇒ 必须审查（阻塞规则使下游等待）。详见「审查义务与审核强度」节。

**路径取最小充分域集合（G22）**：`D* = argmin{|D| : Properties(D) ⊇ Required(T)}`——任务只进入建立其必要性质所需的最小域集合。"天气查询只走需求+调研+验收"**不是跳过**设计/计划/实施，而是这些性质根本不在 Required(T) 中。任何典型路径都是 D* 的结果，不是对全链路做减法：

| 典型任务 | 必要性质 | 路径 D* |
|---|---|---|
| 天气查询 | {WellDefined, Evidence, Closed}（**示例；`Knowledge` 是否列入取决于契约要不要"可复用沉淀"，不是穷举**） | 需求 → 调研（支撑）→ 验收 |
| 实施中遇陌生 SDK | 主任务缺口不变（**其 `Required` 按主任务自己的契约从上表读，通常是 `{WellDefined, Executable, Realized, Evidenced, Closed}`，是否含 `Verified` 看契约**）；支撑任务 `{Evidence, Knowledge}` | 实施 → 调研（supports）→ 实施 |
| 设计并实现一个系统 | 全部核心性质 | 需求 → 设计 → 计划 → 实施 → 审核 → 验收 |
| 批量替换旧域名 | {WellDefined, Maintained, Closed} | 需求 → 维护 → 验收 |

**性质的蕴含关系（决定 D* 会不会重复计域）**：性质之间**不是彼此独立的**——某些性质本身就蕴含另一些，算了后者就不必再单独计一个域。本技能集采用下表；未列出的组合视为无蕴含关系：

| 若已建立 | 则必然也已建立 | 路由后果 |
|---|---|---|
| `Realized` + `Evidenced` | `WellDefined`、`Executable`（**不**蕴含 `Refined`） | 缺 `Realized` 的任务，它的 W/X 缺口通常已由上游满足——不要重复派需求域/计划域 |
| `Verified` | **其被审义务的 subject 在成熟时点已建立**（不蕴含全链先行性质；撤销态除外——Rework 撤销 subject 后义务合取为假而 Verified 可能仍在，以义务合取为准） | `Verified` 的位置由义务成熟涌现：规格审查（subject={WellDefined}）可使 `Verified` 先于 `Evidenced` 建立——**不要再从 `Verified` 反推 `Evidenced` 已建立**；反之，需要 `Evidenced` 的任务仍须让实施域（或其义务）先行 |
| `Refined` | **不蕴含任何其他性质** | 设计域只建立结构，不建立可判定性/可执行性 |
| `Maintained` | **不蕴含任何其他性质** | 维护域只保证既有状态；要重构需另行补齐 Refined/Executable |
| `Evidence`、`Knowledge` | **互不蕴含**，也不蕴含核心链任何一环 | 调研成果不等于任务成立（这正是 `Done(S) ⇏ Done(T)` 的另一面） |
| `Closed` | 由闭合谓词直接给出，不蕴含也不被蕴含 | 它是判定结果，不是"做得更多"换来的性质 |

> **为什么必须写这张表**：不然 D* 的最小化会退化成"性质名数一数"——同一个缺口被两个域各建一次，或者一个域建立了另一个域的性质却被重复派发。表中的"不蕴含"同样重要：它挡住"有了设计就等于可执行"这类想当然的合并。

**复杂度与域解耦（G21）**：`Domain ⊥ Complexity`——复杂度只影响契约大小、任务树深度、证据量、是否需要 Plan、各核心接缝的**审核档位**（G23/G24：轻任务不是"不审"，而是显式免审留痕或轻审）、资源档位，不改变域语义。"今天天气"与"大型平台"的差别只是 `Required(T₁) ≪ Required(T₂)`，而不是任务类型不同。

### 本技能集的默认领域注册表实例（路由可直接执行，不必自行发明性质名）

上面的路由规则要能机械执行，必须知道**每个域到底供给什么性质**。这是本技能集给框架自身用的默认实例（`Action` 列是该域最常见的入口动作；新项目/新能力按同一格式追加行即可，不需要新增流程分支）：

| 域 | 入口 Action（常见） | `required_properties`（开工前应已具备） | `provides_properties`（完成后补齐） | `supports_as_primary` | `supports_as_child` |
|---|---|---|---|---|---|
| 需求 | `specify` | `∅` | `{WellDefined}` | ✅ | ❌ |
| 设计 | `design` | `{WellDefined}` | `{Refined, Invariant}` | ❌ | ❌ |
| 计划 | `plan` | `{Refined, Invariant}` | `{Executable}` | ❌ | ❌ |
| 实施 | `realize` | `{Executable}` | `{Realized, Evidenced}` | ❌ | ❌ |
| 审核 | `verify` | `∅`（**静态**；**动态前提 = 存在成熟且未履行的审查义务**，由调度循环的义务规则承载——审查不被绑定在任何特定性质之后） | `{Verified}` | ❌ | ❌ |
| 验收 | `accept` | `∅`（**动态前提 = 闭合谓词（Done 公式）归动作 gate 承载**） | `{Closed}` | ❌（仅 Publisher 执行） | ❌ |
| 调研 | `research` | `{WellDefined}` | `{Evidence, Knowledge}` | ✅ | ✅ |
| 维护 | `maintain` | `{WellDefined}` | `{Maintained}` | ✅ | ✅ |

> **审核行的可审面注记**：审查义务的 subject 只能取核心链性质去掉 `Verified` 与 `Closed` 本身——可审面 = {WellDefined, Refined, Invariant, Executable, Realized, Evidenced}（审查不能审查审查自身或闭合）。该句限定的是**义务 subject 的取值域**；审核域的对象不限于义务 subject——支撑成果（如调研报告）的核查由调用者另排审核任务承载，不经此路由。`supports_as_child = ❌` 保持不变：审查不以"支撑任务被任意域调用"的方式发生，而是调度循环按义务规则在主路径内插入。
>
> **调研/维护的支撑形态注记**：Support 形态另需调用者声明的输入义务（`RequiredInput(T_p)`，G17 登记四项之一）——那是**任务关系上的登记面**，不是静态 `required_properties`，故不入本表前置列。
>
> **primary=❌ 的边界（防误读，核心五域）**：设计/计划/实施/审核/验收 `primary=❌` 只意味着**根任务链的入口是需求域**（或调研/维护的独立形态）——它**不禁止**这些域的动作出现在任何根任务链的中段（"帮我实现 X"的链是需求 → 实施 → 验收，实施域照常在链中派发），也**不禁止**微任务亲做对应域动作（dispatcher 微任务条款不受影响）。路由始终由缺口计算决定（G16/G22），primary 标志不参与 Gap 计算；它声明的仅是"不存在以该域为入口的独立根任务形态"（与设计文档 §22.4 一致）。

**这张表怎么用**：接到任务 → 写 `Required(T)`（从上表 `provides_properties` 里选）→ 算 `Gap` → 取 `provides_properties ∩ Gap ≠ ∅` 的域 → 按性质依赖序与所需数量取最小集 `D*`。**开工前若发现某域 `required_properties ⊄ Established(T)`，说明路由排错了顺序，先补前置域再派它。**（审核域例外：它的动态前提是义务而非性质——无成熟义务时不派审核，也不算"路由排错"。）

**两处 `∅` 不是同一回事（别读成矛盾）**：
- **需求域**的空 `required` 是**链首职责性质**：界定目标不依赖任何前置性质（它是链条起点）；
- **审核域**的空 `required` 是**动态前提归路由器**：静态不绑定任何性质，但存在"成熟且未履行"的审查义务才入候选（G23 的机制基础）——义务存在与否是契约数据，不是路由器发明的。

**独立调研必须排在需求域之后**（与设计文档 §14.4 交界规则/§16.2 口径一致）：`research` 的静态前置是 `{WellDefined}`——即便用户原话已经给出可判定的目标谓词（"查清 X 是否符合 RFC 9110 第 5.2 节"），`WellDefined` 仍由需求域的 specify 建立后才轮到调研域；此场景下需求域动作很轻（直录谓词即可交接），但**性质建立不可跳过**。只有"查清什么"本身还需要被界定时（"调查一下主流 BIM 轻量化技术"里的"主流/轻量化"未定），需求域才真正承担界定工作。

## 四层结构

| 层 | 定义 | 成员 |
|---|---|---|
| **Core Domain** | 任务核心职责，建立六种核心性质 | 需求、设计、计划、实施、审核、验收 |
| **Support Domain** | 可独立成任务、也可被其他域调用的辅助职责 | 调研、维护 |
| **Service** | 提供能力，自身不承担任务职责 | 知识、记忆、搜索、观测、编排、呈现… |
| **Governance** | 管理权限、责任、状态和闭环（横切） | Publisher、委派、授权、状态、返工、上冒、审计、闭合 |

```text
              ┌──────────────────────────────┐
              │  Governance（横切治理）        │
              └──────────────┬───────────────┘
             ┌───────────────┴────────────────┐
             ▼                                ▼
   ┌────────────────────┐          ┌────────────────────┐
   │    Core Domains    │─supports→│  Support Domains   │
   │ 需求→设计→计划→    │          │  调研 / 维护        │
   │ 实施→审核→验收     │←─────────┤ （也可独立成为根任务）│
   └────────────────────┘          └────────────────────┘
```

支撑域可被任意核心域调用，也可直接作为根任务接受用户委派（G17）。设计文档另定义了**会话域**，本技能集未内化（见文末溯源）。

**正交性判据（判定一个概念属于哪层，问三个问题）**：

1. 它有没有自己的任务契约、工件、证据与完成语义？有 → 它是**域**（核心域或支撑域）；没有 → 它是**服务**或域内**动作（Action）**；
2. 它能不能脱离其他任务单独成立？能 → 它是**支撑域**（可作为根任务被用户直接发布）；只能被调用 → 它是**服务**；
3. 它提供的是"任务完成所**必需**的核心性质"，还是"辅助性质"？必需核心性质（是 Done 公式的必要条件）→ **核心域**；辅助性质（不构成核心链必经环节）→ **支撑域**。注意"必需"≠"必走"：是否必需由 `Required(T)` 声明，不是所有任务都走全部核心域。

按第 3 条判据，审核域是**核心域**：`Verified` 是闭合的必要条件（经 Required 或义务 subject 声明时）；审核的发生位置由契约声明的审查义务决定（见「审查义务与审核强度」节），可在任何核心接缝发生——这不改变其核心域层级。

支撑域定义的两个条件必须**同时成立**（G17）：可独立成任务 ∧ 可被其他域调用。服务不产生 Done Claim，也不被验收。一句话区分域与治理：**域回答"这项工作要建立什么性质、什么时候算做完"；治理回答"谁有权决定、责任归谁、状态怎么走"。**

## 六域总表（跨域对照；域内细节见各域技能）

| 域 | 核心问题 | 建立性质 | 形式化核心 | 典型工件 | 域内条款权威 |
|---|---|---|---|---|---|
| **需求域** | 我们究竟在解决什么问题？ | WellDefined | `R(x) ∈ {True, False}` | spec（目标谓词 + 七问 + 开放问题） | domain-demand |
| **设计域** | 什么结构能保证解决这个问题？ | Refined, Invariant | `D ⊨ R` | arch / 任何结构化方案 | domain-design |
| **计划域** | 如何按合法依赖把目标变成执行路径？ | Executable | `{Pᵢ} Tᵢ {Qᵢ}`，依赖边 `Qᵢ ⇒ Pⱼ` | plan + task 文件 | domain-plan |
| **实施域** | 契约要求的目标状态是否实际出现？ | Realized, Evidenced | `I ⊨ C`；Claim → Proof Obligation → Evidence | 实现产物 + Evidence | domain-implement |
| **审核域** | 为什么可以相信这个结果？ | Verified | `V(A, E, C) ∈ {Pass, Fail, Unknown}` | Verdict / 审查报告 | domain-review |
| **验收域** | 这个任务现在是否可以关闭？ | Closed（**含义见下注**） | `Done(T) ⟺ ContractSatisfied ∧ RequiredVerified ∧ PublisherAccept`（RequiredVerified = 义务合取，见「审查义务与审核强度」节） | Done Claim / 归档 | dispatcher-orchestration（调度者亲做） |

六域构成一条**性质依赖链**——每一环的建立通常以前一环的建立为前提：

```text
Well-defined → Refined → Executable → Realized → Verified → Closed
```

**链上的箭头表示依赖，不表示行程**：它不是"任务必须依次经过的六个阶段"。任务实际进入哪些域，由缺口路由计算的 D* 决定。**审核段的位置由审查义务的成熟涌现**（见「审查义务与审核强度」节）：规格审查在需求域之后即可发生（`Verified` 可先于 `Evidenced` 建立），实施审查在实施与验收之间——同一机制，位置随义务数据变化。

> **"验收域建立 Closed" 的准确含义**：它建立的是**"闭合谓词每一项都有确定的 True/False"**这个性质，而**不是**"任务一定会被关闭"。验收域的输出是**裁决**：Accept / Rework / Reject。**判 Reject 时它同样建立了 Closed**（因为"不满足关闭条件"本身就是一个确定的判定），只是这个已建立的性质使任务**不能**进入 Done。这两件事（建立 Closed / 输出裁决）是同一动作的两面，不矛盾。

**通用化释义（域语义不限于开发）**：需求域负责将**任何用户意图**转换为确定语义的任务规格（"今天天气怎么样"同样能形成判定谓词）；设计域指**任何结构化解决方案**（API 架构、调研方法、报告结构、实验方案、复杂操作的步骤组织）；计划域是**行动可执行化**（竞品调查同样构成依赖 DAG）；实施域 **Implementation ≡ Realization**（写代码、生成报告、执行命令、更新配置、整理数据都是实施）；审核域是对**一切需要被信任的命题**的独立验证。

## 支撑域：调研与维护

**定义**：支撑域是能够**独立形成工作任务**（`Relation(T) = Primary`），同时也可以**被其他域委派调用**（`Relation(T) = Support`），为其提供信息、操作或辅助成果的职责域（G17）。两个条件必须同时成立：只满足"可被调用"的不是支撑域，而是服务。

**调研域的双形态（同一个域，由任务关系区分）**：调研的双重角色不由两个不同的域表示——`Domain(T) = research` 不变——而由**任务图关系** `Relation(T) ∈ {Primary, Support}` 显式承载，二者互斥但穷尽（G17）；必须显式登记，不得靠任务描述或 Agent 角色推断：

- **Primary（独立调研——调研本身是核心域的需求）**：`Result(T) → Goal(T)`——调研构成当前任务的**主要成果**。判据是"调研是否构成当前任务的主要成果"，"用户直接提出"只是常见情形不是判定标准。路径同样由缺口路由决定。
- **Supports（支撑调研——为核心域工作提供支撑）**：`Result(T_s) ⊨ RequiredInput(T_p)`——为父任务提供继续执行所需的信息、证据或决策依据。可嵌入任何域（设计/实施/审核 → 调研 → 原域）。**复杂度与支撑关系正交**：支撑调研同样可以是使用多个域的复杂任务。

| 维度 | 独立调研（Primary） | 支撑调研（Support） |
|---|---|---|
| Publisher | 用户 / 上层任务 | 调用它的主任务 |
| Contract 来源 | 需求域形成的任务规格 | 父任务声明的输入义务 |
| 完成判据 | 自身 Done 公式 | `Useful(S,T)` |
| 进入主路径 | 是（它就是主路径） | 否（supports 关系挂接） |
| 验收 | 自身 Publisher 验收 | 调用者验收成果对主任务的可用性 |

**支撑域 ≠ Action**：Domain 表示工作职责，Action 表示域内具体动作——`research` 拥有自己的任务契约、工件、证据和完成语义，是一等支撑域；`search / retrieve / compare / synthesize` 才是 action，不能把调研降级为某个 action。调研域必产工件：**调研报告（结论 + 依据 + 不确定性声明）+ 来源证据**。

**支撑关系与完成语义**：支撑任务与主任务之间用显式的 **supports** 关系（`S —supports→ T`），区别于普通依赖 **dependsOn**——支撑任务不进入主路径依赖链，不污染核心 DAG。支撑任务的完成**不等于**主任务完成（G18）：

```text
Done(S) ⇏ Done(T)
Done(S) ⇒ Useful(S, T)    （支撑成果满足调用者规定的输入条件）
```

**维护域**：建立性质 `P_维护 = {Maintained}`。简单维护任务最小路径为 需求 → 维护 → 验收（`WellDefined` 由需求域建立，与设计文档 §14.4 交界规则一致）；复杂维护任务按缺口路由补齐（如"重构一个模块"同时缺 Refined 与 Executable，路径同全链）。维护域同样是支撑域：可作根任务直接发布，也可被核心域调用。

**调研的域内工序**（5 类研究型态 × 5 阶段工作流 × 质量红线）见 **research-methodology**；本技能只承载其双形态语义与挂接规则。**维护域暂无独立手册**：其停止/交接/失败处理见上方对照表维护行，操作纪律由调度者在派发契约中按该行内化。

## 核心公式速查

```text
需求可判定   R(x) ∈ {True, False}；相同语义对象判定相同
设计精化     D ⊨ R；分解后 C₁ ∧ … ∧ Cₙ ⇒ R
计划合法     {Pᵢ} Tᵢ {Qᵢ}；依赖边 i→j 须 Qᵢ ⇒ Pⱼ；依赖图是 DAG
实施有据     I ⊨ C；Claim → Proof Obligation → Evidence；Claim ≠ Evidence
审核独立     V(A,E,C) ∈ {Pass, Fail, Unknown}；Unknown ≠ Pass
             可复现 V₁(A,E,C) = V₂(A,E,C)；ProducerClaim ⇏ AuditorVerdict
验收闭合     Done(T) ⟺ ContractSatisfied ∧ RequiredVerified ∧ PublisherAccept
             其中 RequiredVerified ≡ ∀o ∈ Obligations(T): fulfilled(o)（义务合取）——
             缺省义务规则且无撤销发生时退化为 Verified ∈ Established
             ContractSatisfied ≡（契约条款逐条满足）∧（必产工件在场）——
             "缺必产工件"属于 ContractSatisfied 为假，不是 Done 公式的第四项
审查义务     o = {subject, tier, definer}；fulfilled(o) ⟺ 审核已派发 ∧ Verdict=Pass ∧ subject 未被撤销
             无成熟未履行义务 ⇒ 审核不入候选；有 ⇒ 阻塞 subject 相交的下游域（G23 机制）
审核强度     四档免审 < 轻审 < 标准审 < 重审；定档人 = Publisher(被审任务)；只能上调（G24）
域路由       Gap(T) = Required(T) − Established(T)；路径取最小充分域集合 D*（G16/G22）
支撑语义     S —supports→ T：Done(S) ⇏ Done(T)；Done(S) ⇒ Useful(S,T)
             即 Result(S) ⊨ RequiredInput(T)——成果满足调用者规定的输入条件（G18）
双形态判据   Primary：Result(T) → Goal(T)；Support：Result(T_s) ⊨ RequiredInput(T_p)
任务六元组   T = (Publisher, Executor, Contract, Artifact, Evidence, Verdict)
```

### 符号多义映射表（本模型的公式里有几个符号一字多义，执行时按本表落动作）

> 本表存在的理由：`⊨`、`⇒`、`→`、`−` 在本模型里各有两三种读法。**看公式只是压缩表达；落地一律看"判定动作"列。** 本表之外不再单列数理逻辑符号。

| 出现处 | 读作 | 判定动作（拿什么自查） |
|---|---|---|
| `D ⊨ R`（设计精化） | 任何合法符合 D 的实现都满足 R | **反例式自检**：主动构造"合法符合 D 但不满足 R"的行为；构造不出且说得清为什么 → 成立。证据形态见 domain-design §4.2 |
| `I ⊨ C`（实施满足契约） | 契约要求的目标状态已实际出现 | 逐条对照 AC 问"这一条现在是 True 吗、凭什么"；凭可复跑证据 |
| `Result(T_s) ⊨ RequiredInput(T_p)`（支撑成果满足输入义务） | 成果满足调用者**声明的**输入条件 | 拿调用者在登记四项里写下的输入条件逐条对；**"调用者觉得有用"不算**——必须回到那条书面声明 |
| `Qᵢ ⇒ Pⱼ`（依赖边） | 前序的完成状态足以满足后序的开工前置 | 用一句话写出"Qᵢ 怎样满足 Pⱼ"并写进计划；写不出 → 删这条边 |
| `C₁ ∧ … ∧ Cₙ ⇒ R`（分解保契约） | 各局部契约合起来恰好覆盖 R | 做**覆盖矩阵**：逐条 R 标出由哪个 Cᵢ 覆盖；有 R 条目无对应 Cᵢ → 分解不成立（证据形态见 domain-design §4.2） |
| `Done(S) ⇒ Useful(S,T)`（支撑完成） | 支撑任务的责任止于"满足声明的输入条件" | 这是**对调用者的声明义务**，不是对结果的保证；成果实际不满足 → `Useful` 不成立，调用者**验收不通过**（不是审计判 Fail） |
| `⇒`（治理条款里，如 G1/G6） | 若左侧成立则必须触发右侧动作 | 按该 G 规则的"不通过则"列执行 |
| `Result(T) → Goal(T)` / `Claim → Proof Obligation → Evidence` | 前者的 `→` 是"构成/达成"；后者是**转化链**，中间环 `Proof Obligation` 是实体不是修辞 | 转化链的落地：每条 Claim 先写出"别人要复核它需要什么"（= 证明义务），再去取那个东西（= Evidence）；证据形态见 domain-implement §2 与 §4 |
| `Gap(T) = Required(T) − Established(T)` | 集合差 | 逐项对，只看"Required 里哪些还没建立"；Established 里多出来的性质不参与运算也**不影响** |
| `Domain ⊥ Complexity` | 正交（互不决定），不是"矛盾/不可满足" | 检查路由输入里有没有混进复杂度——混进了就是错 |
| `D = D₁ ⊕ … ⊕ Dₙ` | 设计的分解（子设计组合成整体） | 组合形式不限（分层/并行/接口并集都可），但**每层分解都要给 Cᵢ 并过覆盖矩阵** |
| `Domain(T) = f(Required(T), CurrentState(T))` 与 `f(Required − Established)` | 两种写法等价：`CurrentState(T)` 与 `Established(T)` 是同一件事 | 执行时按 `f(Required − Established)` 算即可 |

## 角色模型

治理三角色与域工作者分离（**Domain ≠ Role**：同一角色可出现在不同域，同一域可有多个角色）：

| 治理角色 | 职责 | 本技能集默认映射（v2 按域派发） |
|---|---|---|
| **Publisher** | 发布任务并保留最终关闭权与验收责任 | 人类是顶层 Publisher；调度者（主 Agent）是其委派出去的子任务 Publisher，并兼任**验收域 Worker** |
| **Executor** | 实际执行任务 | **域子代理**（需求/设计/计划/实施/维护各域 Worker；子代理是叶子节点——不能派发孙代理、不能关闭任务） |
| **Auditor** | 独立验证结果与结论 | **审核域子代理**（domain-review，独立上下文）；验证 gate 的实际运行是其证据来源 |

域工作者（角色语义，非治理语义）：Strategist（需求域）、Planner（计划域）、Artisan（实施域）、Auditor（审核域）、Publisher（验收域）。

**审核与验收分离（甲方案的结构性理由）**：审核域子代理回答"命题是否可信"（Verdict），调度者回答"任务是否满足关闭条件"（Accept/Rework/Reject）。若同一个人既写实现/派发契约又自己跑测试复验，Claim 与 Verification 就落在同一上下文里，"命题必须可被独立验证"这条不变量的物理基础（上下文隔离）即告失效。两者的判断分工（M5，跨域裁决条款）：**"证据之合是否覆盖契约条款"（覆盖完整性对照）是验收域的形式判断；"证据是否足以支持结论"（充分性判断）是审核域的判断**——不以"证据充分性"指称验收；若一个判断必须回到原始证据重新推理技术内容，它就是审核域的活。

## Publisher 不变量与多级委派

- **`Publisher(T) = Issuer(T)`**：谁发布任务，谁保留最终关闭这个任务的责任与权力。
- **委派不变量（G11，整个多 Agent 治理模型最重要的不变量）**：`Delegate(T, E) ⇒ Publisher(T) 不变`——委派执行权，不转移最终验收权。`Executor(T) ≠ Publisher(T)` 完全合法。
- **通用任务树语义（G12）**：对任意深度、任意域的任务树，`Done(T_child) ⇏ Done(T_parent)`——子任务完成只能成为父任务的证据（`EvidenceFor(parent)`）的一部分。任务树各级关系**允许/不允许推出**：

| 关系 | 允许推出 | 不允许推出 |
|---|---|---|
| 子任务 → 父任务 | `Done(child)` 是父任务的证据 `EvidenceFor(parent)` | `Done(parent)` |
| 支撑任务 → 主任务 | `Useful(S,T)` | `Done(T)` |
| Executor → Publisher | 执行完成、证据产生 | 任务闭合（Accept 只能由 Publisher 给出） |
| Auditor → Publisher | `Verdict` | `Done(T)` |

  关键不是"多了一层"，而是**每一层都有自己的 Publisher 和自己的闭合谓词**；子任务完成只可能贡献父任务 Done 公式中的 ContractSatisfied 或 Evidence 部分，永远不可能贡献 PublisherAccept（G13）。
- **Publisher 可以不懂技术**：`Accept(T) = f(Contract(T), Verdict(T), PublisherContext(T))`，且 `PublisherAccept ≠ ReVerify(Artifact)`（G9）。Publisher 需要判断的是：契约是否要求这些结果、所需审核是否完成、是否还有未满足的完成条件、有无范围/交付物/责任问题。**验证（Auditor）与验收（Publisher）严格分离。**
- Publisher 的闭合决策三态：**Accept**（关闭条件全满足）/ **Rework**（当前结果仍可修复，保持开放返回执行）/ **Reject**（当前提交不接受且不构成可修复的完成态；出口：重新设计 / 重新计划 / 上冒裁决 / 另立新任务）。

## 审查义务与审核强度（本节是语义权威）

> 本节是审查义务与审核强度的**语义权威**：载体与工序在 dispatcher-orchestration（性质台账 `review_obligations`、派发契约的审核强度节），操作在 domain-review（按档执行）；两处与本节一致，不得另立口径。

**审查义务（Review Obligation）**：契约/派发契约声明的一等数据，随任务签发——

```text
ReviewObligation = { subject, tier, definer }
subject  ⊆ 可审面 = {WellDefined, Refined, Invariant, Executable, Realized, Evidenced}
           （核心链去掉 Verified 与 Closed 本身——审查不能审查审查自身或闭合）
tier     ∈ {免审, 轻审, 标准审, 重审}
definer  = Publisher(被审任务)   ← 定档人
```

**两条规则**（裁决"这个接缝要不要审"时只看这两条）：

1. **使能**：义务成熟（`o.subject ⊆ Established`）且未履行 ⇒ 审核域入路由候选；无成熟未履行义务 ⇒ 审核域不入候选。**审核的发生由契约声明的审查义务决定，不由 Gap(T) 决定**——`Verified ∈ Gap` 而无义务 ⇒ 不审查，路径不变；
2. **阻塞**：成熟未履行义务存在 ⇒ 凡 `required_properties ∩ o.subject ≠ ∅` 的域不入候选——未通过独立审查的性质不作为下游可信前置（G1 的义务推广）。

**履行判定**：`fulfilled(o) ⟺ 审核已派发 ∧ Verdict = Pass ∧ o.subject 未被撤销`。Fail 裁决 ⇒ 撤销 subject ⇒ 义务退回未成熟态，重建后须重新审查。多条义务各自独立取得履行。**成熟单例性**：阻塞规则使前序义务的 subject 阻塞后序 subject 的建立，因此任一时点通常至多一条义务"成熟未履行"；**例外**——多条义务的 subject 由**同一域动作同时供给**（如 {Refined} 与 {Invariant} 均由设计域动作建立）时它们同时成熟，此时按**契约声明序逐个履行**（每条义务各需一次审查 Pass），顺序确定无歧义。

**义务声明的创建期校验（deny-with-reason）**：① subject 非空；② subject ⊆ 可审面；③ subject ⊆ Required(T)（违反者义务永不成熟，或审查任务不要求的性质——两者皆为契约级矛盾）；④ 多条义务 subject 两两不重复。校验不过的契约在创建期即拒绝；仍不可满足的契约由调度循环的不可满足诚实上报兜底。

**缺省与显式**：契约未声明义务时，缺省规则 = `Verified ∈ Required` 产生缺省实施审查义务（subject = {Realized, Evidenced}）；显式声明（含显式免审）覆盖缺省。**每个核心接缝的审查决定（含免审）必须在派发契约中显式声明、留痕，不得静默省略（G23）**——"没写"不等于"免审"。免审的边界（全局口径）：**全部接缝均免审与 `Verified ∈ Required` 不可并存**——此时 Verified 无任何建立通路，是不可满足契约，须拒绝或退回；混合档位不受此限——部分接缝免审、部分在审时，只要存在一条非免审义务能建立 Verified，它就可以合法留在 Required（审核动作恒供给 {Verified}，不随义务 subject 变化）。

**审核强度（Review Intensity）** = 对一次审核**覆盖面**的约定（subject + 维度子集 + 复现深度下限）：

- **四档全序**：免审 < 轻审 < 标准审 < 重审；强度降的是覆盖面，不是标准；
- **定档人 = Publisher(被审任务) = 验收人**（"谁发布谁验收"落到审核环节）。支撑任务被审：`Supports(S,T)` ⇒ 定档人 = `Publisher(T)`；`Primary(S)` ⇒ 定档人 = 用户。**被审域只能申请上调，无定档权**；
- **只能上调（G24）**：定档人可在看到交付物后上调并留痕；任何一方不得下调；
- **红线不随档位放松**：`Unknown ≠ Pass`、不采信转述、不修改被审对象、可复现——所有档位恒成立；
- **未覆盖维度显式标注**：按档执行维度子集后，未覆盖维度必须标注"因档位未覆盖"，不得静默跳过；
- **留痕** = 档位 + 维度子集 + 定档人 + 上调历史。

## 每个域的统一七要素（跨域框架）

为保证各域在架构上一致，每个域应能回答以下问题；**域哲学必须能推出 Agent 的停止条件、交接条件和失败处理**，否则它只是漂亮话：

| 要素 | 必须回答 |
|---|---|
| Philosophy | 为什么这个职责成立？ |
| Worker | 什么角色承担它？ |
| Input | 最少需要什么信息才能工作？ |
| Artifact | 工作完成后产生什么正式结果？ |
| Resource / Failure / Observation | 需要什么能力？什么情况下不能继续？如何知道自己做了什么？ |
| Handoff / Arbitration | 什么结果可以交给下一个职责？什么情况下不能自行决定？ |
| Timing / Refresh | 信息何时失效、何时需要重新计算？ |

各域对这七问的落地位置：domain-demand（需求域）、domain-design（设计域）、domain-plan（计划域）、domain-implement（实施域）、domain-review（审核域）、research-methodology（调研支撑域）、dispatcher-orchestration（验收域与交接/上冒）。

## 领域注册表与性质元数据

路由的物质载体是**领域注册表**：以 `(domain, action)` 为主键，每条目在角色模板/资源/工件等字段之外，携带四项性质元数据——`required_properties`（进入前任务必须已具备的性质，**静态**）、`provides_properties`（完成后为任务补齐的性质）、`supports_as_primary` / `supports_as_child`（可否独立成根任务 / 可否被调用为支撑任务）。路由 = 从 `provides_properties ∩ Gap(T) ≠ ∅` 找候选 → 叠加审查义务使能/阻塞两规则 → 按最小充分条件选 D* → 按性质依赖顺序派发。**新增能力只需登记性质，新增审查点只需声明义务，不需要新增流程分支**（G16/G22/G23）。**审查义务不是注册表字段**：义务是契约数据（随每次任务签发），审核域动作的动态前提（存在成熟未履行义务）由调度循环的义务规则承载，不进注册表（语义见「审查义务与审核强度」节）。

## 各域停止条件、交接条件、失败处理（跨域对照表，权威在本节）

域哲学必须推出行为（七要素硬要求）。本表是**跨域横向对照**，供调度者比对与裁决使用；**各域技能只保留本域那一行**的完整版（子代理需要它来判断何时停止），并注明跨域对照见本技能。

| 域 | 停止条件（算做完） | 交接条件（交给下一职责） | 失败处理（不能继续） |
|---|---|---|---|
| 需求 | 所有不可判定表述已消解或显式标记开放问题；满足条件可判定 | 形成 R：任意候选对象都有确定的 `R(x) ∈ {True,False}` | 无法消解意图 → 上冒（信息不足）；无权界定范围 → 上冒 |
| 设计 | 已给出结构 D，且能论证 `D ⊨ R` | 可分解为带契约的子设计，且 `C₁∧…∧Cₙ ⇒ R` 成立 | 找不到满足 D⊨R 的结构 → 回退需求域；需求自相矛盾 → 上冒 |
| 计划 | 所有步骤有明确前后置条件，依赖图无环且可满足 | 可执行计划：步骤、依赖、前后置条件、并行度 | 设计不可执行 → 回退设计域；依赖无法满足且非设计问题 → 上冒 |
| 实施 | 契约要求的目标状态已出现，且每个正确性声明都有证据 | Artifact + Evidence 足以让独立审核者复现结论 | 设计缺陷 → 回退设计域；证据无法取得（环境/权限）→ 上冒；只有 Claim 无 Evidence → 不得声明完成（G6） |
| 审核 | 按声明档位覆盖维度子集（未覆盖维度显式标注"因档位未覆盖"），对被审核命题给出 Pass/Fail/Unknown 之一，并附判断依据 | Verdict 交定档人（= Publisher，见「审查义务与审核强度」节）接受，使其可在不重复技术复证的前提下闭合 | 契约不清 → 保持 Unknown 并回退契约澄清；环境/权限不足 → 上冒 |
| 验收 | 闭合谓词每一项都有确定 True/False；各段审查义务已履行（Verdict 在场或显式免审留痕） | Done Claim + 终验裁决（Accept/Rework/Reject） | 缺必产工件/范围未覆盖 → Rework；存在未履行审查义务、Verdict 缺失或 Unknown → 不得 Accept |
| 调研（支撑） | 调用者（或需求规格）规定的信息缺口已填满，结论有可复核来源 | 调研工件 + 来源证据；支撑形态额外输出"满足调用者输入条件"的说明 | 关键信息不可获得 → 明示 Unknown 并上冒（信息不足）；无权限访问来源 → 上冒 |
| 维护（支撑） | 既有状态被保持或修复，变更留痕 | 修复后状态交回核心域继续 | 越界改动 → 即停并上冒 |

## 上冒（Escalation）

```text
Escalate ⟺ 信息不足 ∨ 权限不足
```

- 只有这两类情况允许向上冒；其余情况当前域自行解决——不得静默猜测，也不得以判断题反问打断推进。
- 裁决结果向下回填：上层裁决 → 下层恢复执行 → 结果沉淀（memory / 任务文档）。
- **不确定性上冒，确定性下沉。**
- **上冒 / 向人类请求裁决的呈现必须自包含（G25）**：判据 = **提出方只读这一条消息**，能否在不翻前面记录的前提下做出裁决。结构：决策项置顶 → 触发背景 → 已知（已确立 / 已排除）→ 选项与影响 → 不决定的后果与默认；认知预算上限（背景 ≤ 5 行、选项 ≤ 5 个、一屏以内）。**不得把探索成本转移给最缺信息的一方**——人类无法跟踪 Agent 的执行过程，"只给问题不给上下文"等于让最缺信息的人去做探索。

## Why

没有统一的判定依据层，各技能的 gate 只知道"怎么验"、不知道"在验什么性质"：同一规则散落多处各自漂移（"证据亲验"在 dispatcher 是纪律、在 plan-task 是规则，却没人说出 Claim≠Evidence 这个共同根）；"完成"靠感觉而不是谓词；多级委派塌缩成责任真空；支撑调研要么被塞进主路径依赖、要么彻底隐形。G 编号让跨技能引用有公共语言；性质缺口路由让同一套模型覆盖从"今天天气"到"大型平台"的一切任务而不需要为特例新增流程；Done 公式让完成从感觉变成可判定谓词；Publisher 不变量让委派链条保持责任闭环。

## How to apply

遇到"能不能往下走 / 算不算完成 / 该谁验收 / 要不要上冒 / 该走哪些域 / 这个接缝要不要审"类裁决，按序自问：

1. **路由四问（G16/G22/G23）**：这个任务要建立什么性质（Required）？已建立什么（Established）？消除缺口的最小域集合 D* 是什么？有哪些成熟未履行的审查义务（义务使能/阻塞两规则）？
2. **定位后查对应 G 规则**，按规则的"不通过则"行动；
3. **声明完成前对照 Done 公式**三项逐项核对（ContractSatisfied / 义务全履行 / PublisherAccept）；支撑任务对照 Useful(S,T)；
4. **委派时记住 Publisher 不变量**；派发时每个核心接缝显式声明审核档位（G23，免审也须留痕）；复核时输出三值（Unknown ≠ Pass）；只有信息不足或权限不足才上冒。
