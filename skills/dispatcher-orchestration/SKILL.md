# 调度者编排 v2（按域派发的多代理运行时）

> 类型：运行时 / guide｜**读者是主 Agent（你）**，不是域子代理。
>
> 定位：你作为**调度者与决策者**，按域模型把工作拆解为域动作并派发给域子代理。五个域手册（domain-demand / domain-design / domain-plan / domain-implement / domain-review）与 research-methodology 是**各域子代理**的手册，由你在派发时装入；判定依据总层见 **domain-model** 技能。

---

## 一、一句话定位与角色模型

你不亲自做域内工作，而是：**路由（缺口计算）→ 派发（域子代理）→ 交接形式核对 → 循环至缺口为空 → 验收域闭合（你亲做）**。

### 1.1 三个角色与各自边界

| 角色 | 治理角色 | 职责 | 关键纪律 |
|---|---|---|---|
| **主 Agent（你，调度者）** | 受人类委派的 Publisher + **验收域 Worker** + **需求访谈者** | 路由、派发、交接形式核对、集成归档、三态闭合、上冒裁决、台账同步、**需求澄清的合并与追问** | **不亲自做域内工作**（微任务例外）；**不做技术复证**（那是审核域）；**唯一面对需求提出方的声音**（§3.4.1）；上下文只承载判定层信息 |
| **域子代理**（需求/设计/计划/实施/维护） | 对应域的 Executor | 按域技能执行域动作，产出域工件 | 禁止提交代码；禁止越域；域内失败以 Blocked / SupportRequest 回报；**不能派发孙代理** |
| **审核域子代理** | **Auditor** | 对交付物做独立验证（通用审查动作族 + 分域实例化，按声明档位执行），产出三值 Verdict | 只报告不修改；`Unknown ≠ Pass`；**独立上下文**是它成立的前提 |

### 1.2 两条不可让步的结构性约束

**约束一：子代理是叶子节点。** 域子代理只能执行被派发的域动作——不能派发子代理（没有孙代理）、不能发布/关闭任务。因此：
- **验收域职责由你承担**：集成、归档与 Accept/Rework/Reject 闭合决策都由你亲自做出；
- **人类是顶层 Publisher**：plan 级最终归档永远等人类确认，你的 Accept 不能替代它（G11/G13）。

**"不亲自做域内工作"的例外（唯一一类）**：上面的**验收域闭合与集成归档**（§五：更新 task 文件、写 Summary、画 mermaid 类图、commit、mv 归档）是**你亲做的域内动作**——因为**验收域 Worker 就是你**（见 §1.1 表）。除这一类之外，你没有例外。

**叶子的纪律 = 不动定义文件、不做验收**（这条把"不能派孙代理"的边界说完整）：

| 子代理可以自己改 | 子代理不得自己改（改动前必须先回报） |
|---|---|
| 它**本次派发范围内**的产物与它自己的执行记录 | 上游定义文件：`specs/`（需求域）· `archs/`（设计域）· `plans/` 与 task 文件的契约部分（计划域） |
| 它自己的 task 执行记录、证据、债务登记 | 任何它没被授权修改的工件、任何别人的 in-flight 产物 |
| （有疑义时）写"未决事项"回报 | 关闭任务、宣布完成、提交代码 |

**约束二：审核域仍然是独立子代理（不是你自己）。** 你可能想问"既然派发和验收都是我做，为什么验证不也我做"——因为：

> **若你既写派发契约、又自己跑测试复验，Claim 与 Verification 就落在同一个上下文里，"需要被信任的命题必须可以被独立验证"这条不变量的物理基础（上下文隔离）就没有了。**

因此三件事严格分开，**不可互换**：

| 动作 | 谁做 | 产出 |
|---|---|---|
| 跑测试、复跑命令、读 diff 找缺陷 | **审核域子代理** | Verdict（Pass/Fail/Unknown） |
| 对照契约逐条核对、确认无未收口事项 | **你**（验收域） | Closed |
| 宣布"子任务完成" | **你**（Publisher） | Accept / Rework / Reject |

**你的验收操作是「对照」而非「复验」**：你拿 Verdict + 契约做裁决，**不重新检查代码实现、测试细节、异常路径、算法正确性、边界条件**——那些属于 Auditor。

## 二、调度循环：性质缺口驱动 + 审查义务驱动（核心机制）

调度不是固定流水线，而是缺口驱动的派发循环——**调度链由域设计给出、由性质缺口驱动**（G16/G22）；**审核段的发生由契约声明的审查义务决定，不由 Gap 决定**（G23，语义权威见 domain-model「审查义务与审核强度」节）：

```text
循环：
  ① 算缺口    Gap(T) = Required(T) − Established(T)
  ② 查义务    存在成熟未履行的审查义务（o.subject ⊆ Established ∧ 未 fulfilled）
              → 义务成熟 ⇒ 先审：下一步派审核域（使能规则）；
                同时凡 requires 与 o.subject 相交的域暂不派（阻塞规则——未审性质不作下游前置）
  ③ 缺口为空且无成熟义务 → 转验收域（集成/归档/三态闭合；Verified 由审核域建立，Closed 由你建立）
  ④ 选域      依性质依赖序（Well-defined → Refined → Executable → Realized → Verified）
              从"性质→提供域速查表"选出消除当前缺口的域，构成最小充分域集合 D*
  ⑤ 派发      按 §三 派发契约模板装入对应域技能，自包含派发
  ⑥ 交接核对  对照 domain-model「各域停止/交接/失败处理表」+ 该域手册的交接清单，做**形式核对**：
              工件在场、要素齐全、域路径记录完整。
              通过 → Established(T) ∪= 该域性质集 Pᵢ，履行记录同步（见 §2.1），回到 ①
              不通过 → 返工该域（缺陷清单发回同一子代理续作；
                审核域例外：Verdict=Fail 时缺陷发回【被审域】子代理续作，
                并按 §2.1 撤销义务 subject（从 established 移除该性质，fulfilled 退回 false）——
                subject 经被审域重建后方可再次成熟；审核代理仅在有复核需要时续作）
```

> **审核发生由义务决定，非 Gap 决定（易错点）**：`Verified ∈ Gap` 而**无**成熟未履行义务 ⇒ 不派审核，路径照常；有成熟义务 ⇒ 必须先派审核（即使 Gap 计算本身不会选出审核域）。义务是契约声明数据（§2.1 台账承载），不是路由器发明的。

**性质 → 提供域速查表**（**权威实例在 domain-model「默认领域注册表实例」**——含各域 `required_properties`/`provides_properties`/`supports_as_*`；下表是循环用的精简版，两者不一致时以 domain-model 为准）：

| 性质 | 提供域（建立性质集 Pᵢ） | 装入的技能 |
|---|---|---|
| WellDefined（良定义可判定） | 需求域 `{WellDefined}` | domain-demand |
| Refined / Invariant（精化 / 不变量） | 设计域 `{Refined, Invariant}` | domain-design |
| Executable（可执行依赖路径） | 计划域 `{Executable}` | domain-plan |
| Realized / Evidenced（目标状态出现 / 有证据） | 实施域 `{Realized, Evidenced}` | domain-implement |
| Verified（独立验证） | 审核域 `{Verified}`（**入候选前提 = 存在成熟未履行的审查义务**，非 Gap 驱动） | domain-review |
| Closed（闭合） | 验收域（**你亲做**）`{Closed}` | 本技能 §五 |
| Evidence / Knowledge（事实证据 / 可复用知识） | 调研域（支撑）`{Evidence, Knowledge}` | research-methodology |
| Maintained（既有状态保持 / 修复） | 维护域（支撑）`{Maintained}` | **暂无独立手册**：按 domain-model 对照表维护行在契约中内化停止/失败条件 |

**典型展开**：性质全缺时 D* 即全链 需求 → 设计 → 计划 → 实施 → 审核 → 验收（你）——其中审核段的插入位置由各接缝声明的审查义务成熟时点涌现（规格审查义务 ⇒ 需求域后先审；实施审查义务 ⇒ 实施后、验收前）。简单任务的 D* 自动更短（需求 → 维护 → 验收；需求 → 调研 → 验收）——**不是"跳过"，而是那些性质不在 Required(T) 或已由需求域轻量前置建立**（G22：路径是对必要性质的加法，不是对全链路的减法；维护/调研前置见设计文档 §14.4 交界规则，skills 侧同口径见 domain-model「域的本体」调研对称条款）。

**路由时机（触发式）**：任务接单时算一次 Required(T)；此后每轮循环只更新 Established(T)。新插入支撑任务、Reject/Rework 重开时重算。路由结论写入任务文档：`域路径: … ｜ 路由依据: …`。

### 2.1 性质台账：载体、更新时点与语义（Gap 要能算，就必须有地方记）

**粒度（先说清楚）**：`T` 是**单个 task**（或作为根任务的单个任务），**不是整个 plan**。所以路由是**逐 task** 算的：一次路由针对一个 task，得出它自己的 `D*` 与 `域路径`。plan 级只是各 task 台账的汇总，不参与 Gap 计算。

**载体（写在每个 task 文件 frontmatter）**：

```yaml
required_properties: [WellDefined, Realized, Evidenced]   # 本 task 要求最终具备的性质
established: []                                           # 已建立（由你维护，不由子代理改）
review_obligations:                                       # 审查义务台账（subject 可审面以 domain-model 为准，此处不重述）
  - seam: "需求域交接"          # 接缝（哪个域工件产出后审）
    subject: [WellDefined]      # 被审性质集合（⊆ 可审面：核心链 − {Verified, Closed}）
    tier: 轻审                  # 档位 ∈ {轻审, 标准审, 重审}；**免审接缝不写台账条目**（免审是义务的空声明，
                                # 留痕在派发契约第 5 节/任务文档审查决定记录，G23）
    definer: 调度者(代 Publisher) # 定档人 = Publisher(被审任务)；只能上调，上调须追加记录
    fulfilled: false            # 履行态（何时置 true 见更新时点表）
    verdict_anchor: ""          # 履行后记 Verdict 锚点
domain_path: "需求 -> 实施"                                # 域路径（格式见下）
routing_basis: "缺 Realized/Evidenced；WellDefined 已由 spec 建立"   # 路由依据
```

**更新时点表（唯一权威；子代理不得自行改这些字段）**：

| 性质 / 字段 | 何时入集 / 更新 | 记什么值 |
|---|---|---|
| `WellDefined` | 需求域交接形式核对通过 | 记 spec 路径 + status |
| `Refined` / `Invariant` | 设计域交接形式核对通过 | 记 arch 路径 + status |
| `Executable` | 计划域交接形式核对通过 | 记 plan/task 路径 |
| `Realized` / `Evidenced` | 实施域交接形式核对通过 | 记产物面 + 证据落点 |
| `Verified` | 审核域交接形式核对通过（**仅 Verdict=Pass 时入集**；Fail 走下方撤销行；Unknown 不入集、义务保持未履行） | 记 Verdict + 缺陷清单结论 |
| **`established` 撤销（subject）** | 审核 Verdict=Fail 或 Rework 撤销 ⇒ 从 `established` 移除义务 subject 性质并记撤销事件；subject 经被审域重新交接核对重建后方重新成熟（domain-model「审查义务与审核强度」节同口径） | 记撤销性质 + 撤销事件锚点 |
| **`review_obligations[].fulfilled`** | 对应义务的审核 Verdict=Pass 且 subject 未被 Rework 撤销时置 true；Fail/撤销 ⇒ 退回 false（义务退回未成熟态，subject 重建后重新成熟） | 记 Verdict 锚点 + 履行时点 |
| **`review_obligations[].tier` 上调** | 定档人看到交付物后上调（只能上调，G24） | 追加"原档位 → 新档位 + 理由 + 时点" |
| `Closed` | 你做出 Accept 时 | 记裁决 + 依据 |
| `Maintained` / `Evidence` / `Knowledge` | 对应支撑域交接形式核对通过 | 记成果路径 + `Useful` 核对结论 |

**义务何时成熟（判据）**：`o.subject ⊆ Established` 的那一刻该义务成熟。成熟且未履行 ⇒ 调度循环先派审核域（义务使能）；审核 Verdict=Pass 且未撤销 ⇒ fulfilled(o)=true（义务履行）。多义务按 subject 建立序各自成熟、各自履行；**例外**——多条义务的 subject 由同一域动作同时供给（如 {Refined} 与 {Invariant} 均由设计域建立）时同时成熟，按**契约声明序逐个履行**（每条各需一次审查 Pass）。台账创建/更新前先过义务的**创建期校验**（四条：subject 非空、⊆ 可审面、⊆ Required、多条两两不重复——语义见 domain-model「审查义务与审核强度」节），校验不过的契约在创建期即拒绝，不进台账；仍不可满足的契约由调度循环诚实上报（义务使能为叠加口径：review 入候选不受 provides∩gap 过滤，'义务存在但 Verified∉Required'可正常履行）。

**`Established` 的语义（这条必须讲清，否则会与 Claim≠Evidence 表面冲突）**：

> **`Established` = "该性质的工件形式上在场且格式合规"，不是"该结论已被采信"。**

所以：实施域交接通过就可以把 `Evidenced` 入集（证据在那儿了），但**采信**由审核域的 Verdict 决定；`Verified` 入集才代表"结论可信"。**缺口为空 ≠ 可以 Accept**——`Done(T)` 仍然要求义务全履行（`∀o: fulfilled(o)`）与 `PublisherAccept`（见 §五）。

**Requirement 从哪来**：`required_properties` 是你从**契约**读出来的（task 的 AC 与上游 spec 的目标谓词），不是你凭感觉填的；填不出 → 说明契约不完整，按 §五 上冒或在派发前先补上游域。

**两个判据的补齐**：

- **"代价"怎么算**（多个域都能消除同一缺口时的破平）：按序比较——① 性质依赖序更靠前的域优先（先建立前置性质）；② 已装入的域技能可复用的优先（避免重复派发同一本手册）；③ 文件面/读写面更小的优先；④ 仍平手 → **按契约约束**（这里的"契约"指该 task 的 `Acceptance Criteria` 与上游 arch 的 `Interfaces`/`Decision`——**不是** plan 的 Dependency graph，那属于依赖判据而非选域判据），并把选择结果与理由**写进 `routing_basis`**。本四阶梯是运行时精化：它落实 domain-model resolve 第④步"确定性平局规则 + 显式记录"的要求（注册序兜底由"显式记录进 routing_basis"承载），语义争议以 domain-model 为准。
- **性质依赖序与 `D*` 的关系**：`D*` 决定**取哪些域**（最小充分集），依赖序决定**按什么顺序派**。两者并用：先算 `D*`，再按依赖序逐个派；同一轮里没有依赖关系的域可以并行（规则见 §3.5）。

**`domain_path` / `routing_basis` 格式**：一行，`域路径` 用 `->` 连接（含支撑域时标 `(support)`，如 `实施 -> 调研(support) -> 实施 -> 审核`）；`routing_basis` 写"缺什么 + 为什么是这些域"。每轮路由**追加**而非覆盖：用分号追加本轮结论，形如 `[轮1] …; [轮2] …`，保留路由历史（这是可追溯性的一部分）。

### 2.2 终止性（避免无限返工）

- **Rework 上限**：同一个 task 被 Rework **3 次**仍不能通过交接形式核对/Verdict → 停止返工，升级为 **Reject** 或**上冒人类**（并在回报里给出"三次返工的缺陷共性"，让上层能换路径而不是继续磨）。
- **Reject 终局**：Reject 由你做出；出口四选一（回退设计域 / 回退计划域 / 上冒人类裁决 / 另立新任务重开路由三问）。**人类对 Reject 的最终处置有否决权**（你是子任务 Publisher，不是顶层）。
- **循环计数**：把每个 task 的往返轮次记在 `routing_basis` 的历史里，它是上面上限的判据来源。

## 三、逐域派发：契约模板（可复制填空）

**每个域的派发契约必须自包含**——子代理看不到你我的对话，契约是它唯一的上下文。把你希望它知道的一切写进契约，而不是指望它推断。

### 3.1 通用模板

```markdown
# 派发契约：<域>域 / <任务标识>

## 1. 角色与装入技能
你是本次任务的 <域>域 工作者（Executor）。
请先完整阅读并严格遵守：`<域手册绝对路径，如 C:\...\<技能仓>\skills\domain-<x>\SKILL.md>`（作为你的域手册）。

> **路径一律写绝对路径**：技能不在子代理的工作区里（技能仓与项目仓是两个目录），写 `skills/domain-x/SKILL.md` 这类相对路径子代理解析不到。你不知道技能仓的确切位置时，先自行定位再填。
说明：该手册条文自足，只读它即可；其中出现的 G 编号、性质记号是调度者层的引用键，不需要额外查证。
```

### 3.3 支撑任务派发（调研/维护）

**支撑任务的 Publisher 定义**：支撑任务同样有明确的 Publisher 与责任主体——`Supports(S,T)` 形态下 **Publisher(S) = 调用它的主任务**（工程上由你代表主任务发布并验收，判据 = `Useful(S,T)`）；`Primary(S)` 形态下 Publisher 是用户/上层任务。被审支撑任务的审核定档人按此解析：Support 形态 = 主任务 Publisher（通常是你代行），Primary 形态 = 用户。

**支撑形态（Supports）**：以 supports 关系挂接，**不进主路径依赖**；登记四项齐全（形态 / 调用者 / 输入条件 / 出口）；完成判据 = `Useful(S,T)`——成果满足你声明的输入义务，`Done(支撑) ⇏ Done(主任务)`（G17/G18）。

**独立形态（Primary）**：Publisher 是用户/上层任务，完成判据是自身 Done 公式；派发契约里写任务规格（HVQ 即其判定谓词）。派发前**先显式登记 `Relation(T)`**，不得靠描述推断（G17）。

### 3.4 支撑请求闭环（域子代理发现缺口时）

```text
① 域子代理遇信息缺口 → 回报 SupportRequest（缺口 + 建议输入条件）+ 暂停缺口相关工作（无关部分可继续）
② 你登记 supports 四项 → 派发支撑域子代理（装入 research-methodology 或维护条文）
③ 核对 Useful(S,T)：成果是否满足你在输入条件里声明的要求
④ 把成果回填给「原域子代理」（消息续作，不换代理）→ 它继续执行
```

"实施 → 调研 → 实施"在运行时的语义就是**经过你中转**——G17 的"可被调用"指成果归属与判据由调用者定义，不是子代理自行派发。

### 3.4.1 需求访谈闭环（需求域报 Blocked 时，你不是传声筒）

**为什么需要这一节**：需求域是整条链上**唯一必须与人对话**的域——`R(x)` 的判定条件只存在于需求提出方的脑子里，其余域都能自己证/自己排/自己跑。所以"需求域报 Blocked → 追问 → 回填 → 再报"**是正常流程，不是异常**；它可能往返多轮，这是需求澄清的收敛过程。

**唯一对外的声音（单点对外原则）**：

> **只有你面对需求提出方（用户/顶层 Publisher）。域子代理不直接问用户。**

三条理由（任一都足以成立）：① **业务语义的裁定权属于顶层 Publisher**（范围/优先级/阈值/验收口径），下放给叶子子代理会出责任真空；② **并行派发时不能让用户同时被多家子代理打断**——单点对外才能把问题合并成一次问答；③ **答案必须落到工件里**（spec 的开放问题表/已答清单），而工件在你手上；若答案只活在子代理上下文里，它的 session 结束后答案即蒸发，而验收时无从追溯"当初为什么这么定"。

**闭环（与 §3.4 支撑请求闭环并列）**：

```text
① 需求域回报 Blocked（信息不足）→ 内容是一张「决策表单」（表单要求见 domain-demand §4.3.1），不是裸问题清单
② 你做六道加工（见下）→ 合并成一次问答交给需求提出方
③ 收到答复 → 连同「原始意图 + 已回答项 + 未答项」回填给【原需求域子代理】
④ 它在原会话继续（消息续作，不换代理、不重新装配上下文）→ 若仍不足，回到 ①
```

**六道加工（①–④ 是"访谈者"与"传声筒"的分界底线，缺一道就退化成转发；⑤⑥ 是你被授权的扩展加工）**：

| 加工 | 动作 | 判据 |
|---|---|---|
| **① 合并** | 同一轮内多个域同时报缺口 → 合成**一次**问答（头部注明来源：来自需求域 N 项 + 设计域 M 项） | 需求提出方本轮只被打断一次 |
| **② 给候选** | 把裸问题补成「候选答案 + 各自后果 + 推荐项」（子代理应该已经给了；没给就发回它补） | 每条问都能被"选一个"而不是"写一段" |
| **③ 给影响面** | 标注该问题**影响 R 的哪一条** | 需求提出方能判断"不答会怎样" |
| **④ 能推不问** | **事实性**缺口（外部技术事实、既有代码现状）→ 派调研/维护去查，**不要拿去问人**；只把**业务语义类**（范围、优先级、阈值、验收口径、非目标）留给需求提出方 | 问出去的都是只有人能答的 |
| **⑤ 拆题**（你被授权的加工，不只是补候选） | 一题里塞了两个决策（如"阈值与负载"）→ **拆成两题**，各自给候选/影响/默认 | 对方能一题一答，不会答了半边 |
| **⑥ 改问法**（授权，但有界） | 问题太抽象/候选不贴身 → 改写问法或把"开放问"转成"选择题"（见下方收敛纪律的处置 (a)） | 你能**改问法**，但**不能替它编业务语义**——缺候选/缺默认时发回子代理（见下） |

**合并的三条纪律（多域同时报缺口时）**：

1. **先质疑前提**：按性质依赖序，设计域依赖 `WellDefined`——同一 task 上需求域还没闭合时，设计域**本不该被派**。真出现同轮报缺口 → 先判它是"误派"还是"它卡的不是本 task 的 R"，别急着合并。
2. **只并可独立回答的项**：若设计域的接口取舍**必须先知道 R 才能问准**，就不并入本轮——留到下一轮并在记账里记为 pending。**否则等于问一个还问不准的问题**，违反"每条问都能被选一个"。
3. **答复按来源拆开回填**：一次问答出去，答案要**分别回填给原需求域子代理与原设计域子代理**（各自原会话），不是回填给同一家。

**回报格式（你要发给需求提出方的；统一自包含模板，G25——需求访谈与 §六 上冒两个通道共用同一结构）**：

```text
【需要你决定：<一句话结论，决策项放最前>】——需求澄清 <任务标识>，共 N 项，预计 1 轮可答完

■ 背景：因为 <触发事件>，所以需要这个决定
  （若多条来源，注明已合并：来自需求域 N 项 + 已用调研解决 M 项）

■ 已知（已确立 / 已排除）：
  - 已确立：<事实 + 证据锚点>
  - 已排除：<试过什么、为什么不行>          ← 最省用户时间的一栏

■ 选项与影响：
  1) <问题>
     候选： (a) …（推荐：因为…）  (b) …  (c) …
     影响： <它决定 R 的哪一条 / 下游哪个域>
     默认： <若你无偏好，我按 X 起草并在 spec 开放问题里标注"待确认">
  2) …

■ 不决定的后果，与默认：<不加干预会怎样 / 我按 X 起草并标注待确认>
```

**认知预算上限与判据（G25，硬要求）**：背景 ≤ 5 行；每题选项 ≤ 5 个；总长控制在一屏内。**判据（可判定）：用户只读这一条消息，能否在不翻前面记录的前提下做出决定**——不能，就说明"已确立 / 已排除"两栏没写够，退回重写；**不得把探索成本转移给最缺信息的一方**（人类无法跟踪 Agent 的执行过程）。

**为什么必须给"默认"**：不给默认会让"用户不关心"变成"流程卡死"。默认值 + 显式标注待确认，让流程能在用户不表态时继续推进，同时不伪造确定性（公理 3 禁止的是**冒充已确定/隐式假设**，不是"在标注不确定的前提下取默认"）。

**默认值归谁**：

> **默认值由需求域子代理提出（它最了解问题语境：哪个候选最贴近用户原话、哪个后果最轻）**
> **你只负责转述与润色，不负责发明。**

| 情形 | 你做什么 |
|---|---|
| 子代理给了默认 | 转述（可调整人称与措辞，**不改选项内容**） |
| 子代理**没给**默认，或候选明显不贴身 | **发回【原需求域子代理】补**（消息续作），不要自己编 |

**为什么不能自己编**：默认值是**业务语义**（"不表态时按哪个口径推进"），不是格式加工。你编一个默认 = 替需求提出方做了业务裁定，且这个裁定会**悄悄进 spec**（标了"待确认"也一样会引导下游）——这正是 §3.4.1 单点对外要防的东西，与"不让子代理直接问用户"是同一枚硬币的两面。

**"加工候选"与"编造答案"的硬判据**：

> **每个候选都必须能填出来源**——用户原话的派生 / 既有工件的引用 / 外部事实（已由 SupportRequest 查到）/ 历史记录（既有记录，须标漂移风险）。**填不出来源 → 不是加工，是编造，删掉或发回子代理。**

所以**"把裸问句补成选择题"是你的加工权限**（把已有素材组织成可选项），**"想几个我猜的选项"不是**。两者的区别不在"有没有标待确认"（那是软边界），而在**候选有没有 provenance**（这是硬判据）。发回子代理时也照这条要求它：每个候选带来源，否则退回来。

**成本是显式的**：缺默认会导致"发回子代理 → 再拿回来"的一次**内部往返**（不占用需求提出方的时间）。这个往返不计入收敛轮次（见下），但会拖慢一轮。**所以派发需求域时在契约里提醒它：决策表单必须自带默认**（domain-demand §4.3.1 九条要求之第 4 条）。

**收敛纪律（不设硬上限，但要证明在收敛）**：

- 需求澄清**不设往返次数硬上限**（它是收敛过程，且硬上限会逼出"为不超限而编默认值"）；
- 但**每一轮你必须在回报里写明"本轮缩小了哪些不确定性"**：把上一轮的缺口表单与这一轮的缺口表单对比，**若一轮问完没有任何项被消解 → 停下换问法或直接上冒人类**（说明问法有问题，继续问只是重复消耗）；
- 判据一句话：**这一轮之后，能被问的东西是不是真的变少了？** 没变少 → 别再来一轮。

**"一轮"怎么算**：**只算"发给需求提出方并收到答复"的往返**。以下**不计入**轮次：① 发回子代理补候选/补默认的内部往返；② 派调研/维护查事实的往返；③ 你内部的合并加工。理由：那些都是**不占用提出方时间**的加工；把它们计入会污染"收敛"这个度量。

**合并窗口**：**窗口在你发出问答的瞬间关闭。** 之后才到达的 Blocked（如设计域迟一步报缺口）**并入下一次问答**，不要为了凑合并而阻塞已就绪的问答——空等会把"只打断一次"变成"更晚才打断"。**唯一例外**：若你**已经知道**另一域本轮会报缺口（例如你刚派了它且它必然要问），可以短暂等它的回报再合并（上限：一次同轮等待，不轮流等）。

**"能推不问"是并行而非串行**：派调研/维护查事实与向需求提出方提问**同时进行**，不要等调研回来才发问答——事实项只影响被测口径等细节，通常不影响业务子句的候选。调研结论回来后，写进 spec 的"判定方式"栏（`domain-demand` §一），不占提出方的决策时间。

### 3.5 并行派发规则

- 计划域产出的依赖 DAG 中，**文件面零交集且依赖已满足**的 task 可并行派发多个实施域子代理；
- **同文件改动必须串行**；
- 并行时在契约第 2 节写入**并发在途变更告警**，防证据交叉污染；
- 审核阶段对并行产物按**时间戳/归属**隔离审查（否则会把他人改动误判为交付缺陷）。

**"依赖已满足"的准确含义**：
- 指前置 task 的 `Q`（完成状态）已**形式上建立**——即它已通过实施域交接形式核对。**不要求**前置 task 已 Accept（Accept 还要等 Verdict，等它会不必要地串行化整条链）。
- **例外**：若前置 task 正处于 Rework，或 Verdict=Unknown 且有返工风险，则后继 task **必须等**——它的开工前置可能被推翻，提前开工等于在流沙上施工。判据：**前置的结论现在还可能变吗？** 会 → 等；不会 → 可派。
- **依赖边判据优先于文件面判据**：`Qᵢ⇒Pⱼ` 是依赖的唯一依据（G5），文件面零交集只是"能不能安全并行"的附加条件。有依赖边但文件面零交集 → **必须串行**（语义依赖也是依赖）；无依赖边但文件面相交 → **必须串行**（物理冲突）。**任一命中即串行。**
- **phase 边界本身不构成串行门**（显式条款）：phase 只是"可独立验收的交付段"的分组。**phase-2 的 task 不必等 phase-1 的全部 task Accept**——它只等**自己依赖边指向的那些 task**。若某个 phase-2 task 与 phase-1 毫无依赖关系，它可以和 phase-1 的 task 同时派发。**判据只看该 task 自己的 `depends_on` 与文件面，不看它属于哪个 phase。**

## 四、交接形式核对：各域清单（通过则更新 Established）

核对是**形式核对**：工件在场、要素齐全、格式合规。**技术验证只由审核域建立，你不在交接时复验。**

**边界怎么判"形式"与"技术"**（这是最容易踩线的地方，给两条可执行判据）：

| 你能做（形式核对） | 你不能做（技术复证，属审核域） |
|---|---|
| 看"D⊨R 论证段在不在、有没有构造反例的痕迹、有没有写"为什么构造不出"" | 判断那个论证在技术上站不站得住 |
| 看"gate 有没有跑过、输出在场不在、勾选项下有没有输出" | 自己再跑一遍 gate 去验证输出是否真实 |
| 看"AC 逐条是否都可判定、是否都能找到对应证据行" | 判断某条 AC 在实现上到底满不满足 |
| 看"债务有没有三处登记、编号有没有顺延" | 判断那条债务该不该这么归类 |

**一句话判据**：我是在**核对"有没有做、够不够格"**，还是在**核对"做得对不对"**？前者的证据是可以"看"出来的（在场/格式/计数），后者必须重新执行或重新推理——那就是审核域的活。

**plan 级与 task 级的分工（别把两层揉在一起）**：

- **task 级验收**：拿该 task 的 AC 与 Verdict 做闭合，只针对这个 task 的交付面；
- **plan 级归档**：核对 plan 级的整体契约（plan 的 Dependency graph、各 phase 的 Q 是否串起来、跨 task 的接口是否一致）与 **spec 的目标谓词**（它是 plan 存在的理由，归档前必须确认它成立）。**spec 的目标谓词由审核域在证据层面确认（Verdict），你在归档时只做"有没有这一条、结论是什么"的形式对照。**

**核对清单的权威位置 = 各域技能自己的「交接清单」**（单点真相：清单只在域技能成文一次，本文不复述）。本表只做**索引**：告诉你去哪份手册打勾、以及**该域交接物是什么**。

**发布者的额外形式核对项（G23/M5）**：task 级验收时，除了逐域交接清单，你还须形式核对——**各核心接缝的审查决定在场**：每道接缝要么有对应 Verdict（义务已履行），要么是显式免审档且有留痕（派发契约第 5 节/任务文档审查决定记录可查；免审不写 `review_obligations` 台账）。缺 Verdict 又无免审留痕 = 静默省略，违反 G23，不得 Accept。这是"核对在场与否"的形式判断，不是技术判断（M5 分工不变：证据是否足以支持结论仍归审核域）。

| 域 | 交接物 | 核对该域手册的哪一节 |
|---|---|---|
| 需求域 | spec 文件 | domain-demand §4.2 交接清单 |
| 设计域 | arch 文件 | domain-design §4.3 交接清单（**含 Gate A/B/C，勿只过 A/B**） |
| 计划域 | plan + task 文件集 | domain-plan §4.2 交接清单 |
| 实施域 | 工作区产物 + 更新后的 task 文件 | domain-implement §4.5 交付打包（四件套） |
| 审核域 | Verdict + 缺陷清单 | domain-review §4.1 回报格式 + §4.2 停止/交接条件 |
| 支撑域（调研） | 调研工件 + 来源证据 | research-methodology §7.2 交接清单 |
| 支撑域（维护） | 变更后的既有状态 + 变更留痕 | **本项目/本技能集暂无独立维护域手册**——按 domain-model「各域停止条件对照表」的维护行（停止=既有状态被保持或修复、变更留痕；失败=越界改动即停并上冒）核对，并在契约里把该停止条件显式写给子代理 |

> **为什么不再复述一份**：本文与域技能各写一份核对清单，第一次改动就会漂移（实测已漂移：本文曾漏写设计域的 Gate C 与"status 停 proposed 的说明"）。域技能是子代理唯一的手册，清单理应在那里。

**核对不通过 → 返工**：把缺陷清单发回**同一**子代理续作（消息续作，上下文延续）。**核对通过 → 按 §2.1 的"更新时点表"把该域性质写入 task frontmatter 的 `established`，回到缺口循环。**（注意：入集 = 工件形式上在场，**不等于**结论已采信——采信归审核域 Verdict，见 §2.1 语义说明。）

## 五、验收域（你亲做）：三态闭合与集成归档

### 5.1 审核与验收是两件事

```text
审核域回答：这个命题是否可信？        → 审核子代理 → Verdict（Pass/Fail/Unknown）
验收域回答：这个任务是否满足关闭条件？ → 你（Publisher = Issuer） → Accept/Rework/Reject
```

```text
Done(T) ⟺ ContractSatisfied ∧ RequiredVerified ∧ PublisherAccept
         ＝ 契约逐条满足    ∧ 义务全履行        ∧ 你确认关闭
  其中 RequiredVerified ≡ ∀o ∈ review_obligations: fulfilled(o)
  （缺省义务规则且无撤销发生时退化为 Verified ∈ Established；Rework 撤销场景以义务合取为准——语义权威见 domain-model）
```

### 5.2 你的验收操作（对照，而非复验）

你的验收是**覆盖完整性对照**（M5）：把契约条款与在场证据 / 裁决逐条对照——"每一条条款是否都有在场证据或裁决覆盖"是形式判断；"证据是否足以支持结论"归审核域（M5 分工，权威见 domain-model「角色模型」节（审核与验收分离段）与 domain-review §5.1），你不做、也不需要做。

1. **各段 Verdict 在场且 Pass，或显式免审留痕**——不得 Accept。分处置：Verdict 缺失或 Unknown → 先派审核域；免审档无留痕 → 定档人补记免审留痕（或经 G24 上调后走审核）。免审接缝本无 Verdict，不适用 Unknown 判据。
   - **与审查义务的关系**：**契约声明了审查义务就必派审核（或该接缝显式免审且留痕）**——判据是 `review_obligations` 台账（G23），不是你临场判断"要不要审"。义务 subject 已建立且未履行 → 调度循环的义务使能规则早已把审核排进队列（§二 步骤②）；走到验收还欠 Verdict，说明循环被跳过，先补审再回来。
   - **与 `Verified ∈ Required` 的关系（向后兼容）**：task 的 `required_properties` 含 `Verified` ⇒ 至少存在缺省实施审查义务；不含 `Verified` 且无显式义务 ⇒ 不要求 Verdict，Done 公式的 `RequiredVerified` 项按"无义务"自然满足，**其余两项照旧**（契约逐条满足 + 你确认关闭）。**判据一句话：义务台账决定要不要 Verdict；台账空白时退回看 `Verified` 在不在 Required 里。**
2. **拿契约逐条核对**（task 的 Acceptance Criteria / spec 的目标谓词）——逐条标注"在场证据 / 裁决"覆盖；
3. **确认无未收口事项**（债务、arch 偏差）；
4. **核对义务台账闭合**：`review_obligations` 无"subject 已建立但未履行"的悬挂项（有 → 回步骤 1）。

### 5.2.1 验收与归档的时点（两张表，别混）

| 时点 | 触发 | 你做什么 | 门禁强度 |
|---|---|---|---|
| **task 级 Accept** | 该 task 的 Verdict=Pass + 契约对照通过 | 确认"无待处理事项"（登记表形式检查：有没有未登记的债务/未记的偏差）；**不做**归档九步 | 轻量：只确认没有漏登记的，不核销 |
| **plan 级归档** | plan 下**全部 task 完成** **且** 人类确认"可以归档" | 执行 §5.4 九步（含 arch 偏差与债务终态两道硬 gate） | 重量：逐条核销、跑两道硬 gate |

**这就解开了 §5.3 与 §5.4 的表面矛盾**：§5.3 说 Accept 后"走归档九步"，指的是**当 plan 已全部完成**时的出口；plan 未完成时 accept 完就回缺口循环。§5.4 的"等人类确认"**只对 plan 级归档生效**，不是每个 task 都要等一次人类。

**若在 task 级发现未收口事项**：不阻塞 Accept（那是 plan 级的事），但必须在 `## 债务与偿还条件` / 偏差注记里**登记**，并写入回报；到 plan 级归档时它会被 §5.4 第 4/5 步的硬 gate 拦住。**登记与核销是两件事，登记可以早、核销只能在归档做。**

### 5.3 三态闭合

| 裁决 | 条件 | 出口 |
|---|---|---|
| **Accept** | 三项齐（契约满足 ∧ 义务全履行 `∀o: fulfilled(o)` ∧ 你确认） | 走 §5.4 集成归档九步 |
| **Rework** | 当前结果仍可修复 | 缺陷清单发回**同一**域子代理续作（上下文延续），复核闭环后再集成 |
| **Reject** | 当前提交不接受且不构成可修复的完成态（终局态） | 四选一：回退设计域 / 回退计划域 / 上冒人类裁决 / 另立新任务（重开路由三问） |

**单 task 闭合 ⇏ plan 闭合**：每个 task 的闭环只是 plan 级验收的证据之一；plan 级最终归档等人类确认（顶层 Publisher）。

### 5.4 集成归档九步（plan 下全部 task 完成后，**等人类确认"可以归档"再执行**）

1. **更新 task 文件**：`## Checklist` 所有 `[ ]` 改 `[x]`；追加 `## Changelog`（日期 + 状态、每个 checkpoint 实际产出、关键修复 bug+root cause+fix、未覆盖边缘 case）；`## 债务与偿还条件` 逐条对账（REPAID 附行为证据，OPEN 确认已入登记簿并接线）
2. **任务总结 `## Summary`**（聚焦过程和决策）：问题处理（阻塞/排查路径/解决）、决策变更（plan 设计被改了什么、为什么）、绕过或延后项及原因
3. **生成核心代码结构关系类图（mermaid）**：在 Summary 前追加 `## 核心代码结构关系（类图）`。**范围界定——只画本 phase 真正改/加/动的代码**（打开 git diff 看实际改动行；✅ 新增类/改签名类/核心链路依赖/跨模块新依赖/决策强绑定 value object；❌ 仅引用未改的旧类/整个模块/调用栈外围工具函数/通用语言类型）。**Mermaid 语法约束**：❌ 内联对象类型 `{x,y}` → ✅ 展平为独立 value object class；❌ 字面量/`readonly` → ✅ 基础类型；❌ 方法名后 `?` → ✅ 移除并在注释说明；❌ 泛型完整写法 → ✅ 简化或 `~` 转义；❌ 裸文本行 → ✅ 正式方法签名；❌ 文件路径当节点 → ✅ 移到图外表格；✅ 提交前 `mmdc -i diagram.mmd -o out.svg` 验证
4. **arch 偏差检查（硬 gate）**：对比实际实现与 plan `arch:` 指向的 accepted arch，三选一——**零偏差**（符合 Decision/Architecture/Interfaces）直接 proceed；**轻微偏差**（落在 Open Questions 范围内/实现细节调整）task Summary 追加 `### Arch 偏差`（偏差点+原因+仍属 arch 范围的理由）后 proceed；**核心偏差**（改了 Decision 关键选择/替换对外 Interfaces/改数据流或模块边界）**禁止归档**——先回设计域走 supersede 链新建 arch、迁移 plan 的 `arch:` 指向再继续
5. **债务终态核销（硬 gate）**：核对债务台账（多 task plan = `DEBT-REGISTRY.md`，单 task = 各 task 债务节）：全部 OPEN 债务 REPAID（附行为证据）或显式处置/移交；存在"无到期日期的中间态"则禁止归档
6. **提交 commit**：仅 stage 当前 plan 相关文件；`git diff --cached --stat` 验证；message 格式 `feat(<scope>): <简要描述> (plan <NN>)`
7. **写入 githash**：commit hash 写入每个 task 文件 frontmatter `githash: <hash>`（status 之前）
8. **更新 plan 文件**：changed files 实际列表、新增 design decisions 同步
9. **归档 task 文件**：`status: completed` 的 task `mv` 到 `archive/`；同步更新 plan 文件中的 task 链接路径；**归档 mv + plan 路径更新 + githash 合并为一次原子 commit**

## 六、治理纪律

- **委派不变量（G11）**：派发执行不转移验收责任——子代理完成 ≠ 你可关闭（须交接核对 + Verdict）；你的 Accept ≠ 人类确认（plan 级归档永远等人类，G13）。
- **任务树（G12）**：每个 task / 支撑任务有自己的 Publisher 与闭合谓词；子任务 Done 只是 `EvidenceFor(parent)` 的一部分。
- **上冒链（G15）**：域子代理遇信息不足/权限不足 → 回报 Blocked（不静默猜测、不自行扩大范围）；你无法裁决 → 上冒人类；裁决结果向下回填（下层恢复执行 → 结果沉淀）。
  - **上冒消息采用与 §3.4.1 需求访谈同一自包含模板（G25 高风险通道）**：决策项置顶 → 背景 → 已确立/已排除 → 选项与影响 → 不决定的后果与默认；认知预算上限同（背景 ≤ 5 行、选项 ≤ 5、一屏）。判据：**人类只读这一条上冒消息即可裁决**。
  - **上冒前必须加工，不得原样转发**：把子代理的 Blocked 直接丢给人类 = 传声筒。至少做 §3.4.1 的六道加工（合并 / 给候选 / 给影响面 / 能推不问 / 拆题 / 改问法），**先自己消解能消解的部分**，再把剩下真正需要人裁定的交上去。判据：**我交上去的每一条，是不是都只有人能答？** 有我能查的混在里面 → 退回去先查。
- **微任务亲做条款（G21 资源档位）**：单文件/单点的极微任务（一行替换、一个快速修正），派发开销大于收益时可由你亲做，但必须按对应域技能条文执行并在任务文档留痕，**留痕要素固定为四项：`域路径` / `目标谓词`（或等价判据）/ `结果` / `证据`**——这是派发的退化形态，不是跳过域。**接缝审查决定（含免审）一并留痕**（G23：免审写明理由，非免审按台账登记义务）。
- **踩坑沉淀**：域子代理回报的坑/反直觉行为，按 memory-knowledge-system 即时沉淀 feedback，不攒批。
- **台账核对（开工前置）**：每轮派发实施域前核对债务台账——到期未清偿不得开工；顺路偿还型债务接线为该 task 首项。
- **效率原则**：消息续作（返工/追问走原代理会话，不新开）；上下文保护（大段 diff/输出由子代理消化，你只读结论表与缺陷清单）；前置复核降级（plan 中后期 phase 计划已稳定时按需触发）。
  - **会话续作是你的契约义务，不只是效率偏好**：需求访谈（§3.4.1）与返工（§5.3）都向子代理承诺了"答复/缺陷清单回填到你当前的会话，你接着做，**不会让你重来一遍**"。要兑现这句承诺，你必须：① **派发有往返预期的域任务时（需求域、实施域返工、审核域复核）用可续作的子代理会话，不要用一次性执行**；② 内部往返（发回补候选/补默认）也走同一会话。**若你改用一次性执行，那句承诺就是假的**——子代理会重读材料、重问已答项。**契约第 1 节据此写一句**：`本次派发可能有多轮往返，你必须能在原会话被唤醒续作；不要在回报后丢弃上下文。`
- **质量红线**：验证分工——技术复证属于审核域子代理（亲自复跑、不采信转述），你采信的是 Verdict；无 Verdict 的"完成声明"不进入集成；三值结论（Unknown≠Pass）；数字不篡改（口径问题只注记+记录实际值）；禁区纪律（子代理改动面可枚举，越界即返工）；归档原子性（githash+归档+链接+台账一次 commit）。

## 七、已知陷阱（实战沉淀，派发与复核时对照）

- **并发污染**：并行子代理的在途产物会污染彼此证据——校验产物时间戳/归属，必要时交叉隔离实验（A vs A-prime 差异恰为受控变量）证因果；
- **行号时效**：任务文档行号在实现后失效——复核按实际源码核对引用，不沿用文档旧值；
- **恒真断言**：无随机函数的双跑对比结构性恒真——形式性检查须注明其证据强度由哪项实质门控承载；
- **理想口径不可满足**：以参照形态为锚的门槛可能在自身语义下不可达——执行期校准需独立复核 + 落注记，锚改为可判定的证据化条件；
- **不可见字符差异**：文档编辑失败多为全半角/引号差异——用短锚点或按行精确匹配；
- **产物命名污染**：多次转换产物勿覆盖历史（递增命名），对比基线才可回溯；
- **审核退化为确认**：若把"跑测试"当成审核的全部，实现合理性维会缺失——派审核域时在契约第 4 节显式要求"通用审查动作族 + 分域实例化逐项结论"（domain-review §三）；
- **契约省略导致子代理猜**：派发契约少写一节（尤其是禁区、审核强度、基线归属、回报格式），子代理必然按自己的默认假设行事——模板八节不是可选项。
- **把审核触发说成缺口决定**（易错点）：审核的发生由**契约声明的审查义务**决定（G23），不由 Gap(T) 决定——`Verified ∈ Gap` 而无义务 ⇒ 不派审核；有成熟义务 ⇒ 必须派（义务阻塞下游）。把两者混说会导致：要么无义务硬派审核（强迫全链），要么有义务漏派审核（未审性质流入下游）。
- **把需求域的 Blocked 当终点**：需求域报"信息不足"是**正常流程的一环**（它必须问人），不是失败；正确动作是走 §3.4.1 需求访谈闭环。若你把它当成"这活儿做不了"而停下或反复原样转发，就是把交互式澄清当成了单次委托。
- **需求澄清不做收敛记账**：每一轮必须能说出"本轮消解了哪些不确定性"；说不出来还继续问，是烧 token 而不是推进（§3.4.1 收敛纪律）。
- **让子代理直接问用户**：会同时破坏单点对外、答案落盘与权限纪律三条（§3.4.1）。**只有你面对需求提出方。**
