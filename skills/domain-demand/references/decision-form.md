# 「决策表单」：信息不足时的回报格式

> **何时读**：判定为"信息不足"、要产出决策表单回报前读（模板、九条要求、来源判据、推荐与默认的分界、收敛自检）

### 4.3.1 「决策表单」：信息不足时的回报格式（本域最重要的产出形态之一）

**为什么要用表单而不是问题清单**：你的回报会被调度者加工后交给需求提出方。**"问题清单"要求对方动脑组答案；"决策表单"只要求对方选一个**——后者才能让澄清在一两轮内收敛。裸问题是把工作推给了提出方，表单是把工作做在你这侧。

**自包含要求（G25，与调度者侧模板同构）**：提出方**只读你这一个回合的表单**就要能裁决——"已确立 / 已排除"两栏写足，不得让对方翻之前的记录。

```text
【需要你决定：<一句话结论>】——需求域 决策表单 <任务标识>，共 N 项

■ 背景：因为 <触发事件>，所以需要这个决定（≤5 行；我已读了什么、当前卡在哪）

■ 已知（已确立 / 已排除）：
  - 已确立：<事实 + 证据锚点>
  - 已排除：<试过什么、为什么不行>          ← 最省对方时间的一栏

■ 选项与影响：
  1) <问题，一句话>
     候选： (a) <选项>（推荐：因为…）   (b) <选项>   (c) <选项>
     影响： <它决定 R 的哪一条子句 / 哪个判定方式>
     默认： <若对方无偏好，我按 X 起草并在 spec 开放问题里标注"待确认">
  2) …

■ 不决定的后果，与默认：<不加干预会怎样 / 我按 X 起草并标注待确认>

<可附：我建议的处理顺序、哪些项可以先答、哪些项必须一起答>
```

**认知预算上限**：背景 ≤ 5 行；每题选项 ≤ 5 个；总长控制在一屏内。**判据（可判定）：提出方只读这一条消息能否做出决定**——调度者会按此验收你的表单，不达标的会被退回补"已确立 / 已排除"。

**先分清"推荐"与"默认"（两条要求语义重叠，这里定义死）**：

| | 推荐 | 默认 |
|---|---|---|
| 回答的问题 | **"应该选哪个"**（我的判断，带依据） | **"对方不表态时怎么办"**（兜底草案） |
| 依据 | 必须有：用户原话派生 / 既有工件引用 / 外部事实 | 不要求依据（它就是"无答复时的推进方式"） |
| 语气 | "推荐 (a)，因为…" | "若您无偏好，我按 (a) 起草并在开放问题标注『待确认』" |
| 无业务依据时怎么写 | **如实写**：`推荐：无业务依据，仅按 (a) 起草（可反驳）` | 照常写兜底值 |

**无依据时给"占位值"不是编答案**（公理 3 禁止的是**编判定条件冒充已确定**，不是"在显式标注待确认的前提下取兜底值"）。判据：**你有没有说清"这只是占位"？** 说了 → 合规；没说、让对方以为这是你的结论 → 违规。

**表单的要求（缺一条就会被退回来补）**：

| # | 要求 | 反例 |
|---|---|---|
| 1 | **每题必须有候选**（≥2 个），不能是开放问句 | ❌ "你想怎么测性能？" |
| 2 | **必须标推荐项与理由** | ❌ 只列 a/b/c 不说推荐哪个 |
| 3 | **必须写影响面**（它决定 R 的哪一条） | ❌ 不说为什么要问 |
| 4 | **必须给默认**（并说明"标注待确认"而非"冒充已确定"） | ❌ 不给默认，对方不答就卡死 |
| 5 | **能自己查的不要问**（外部技术事实、既有代码现状 → 走 SupportRequest） | ❌ 把"这个 SDK 怎么用"混进业务问题里 |
| 6 | **一题一义**（不要把两个决策塞进一题） | ❌ "导出什么格式、给谁用？" |
| 7 | **每个候选必须有来源**（见下） | ❌ 凭空想出来的选项 |
| 8 | **必须有「已确立 / 已排除」两栏**（自包含判据：提出方只读本表单即可裁决，G25） | ❌ 只给问题，让对方自己翻之前的记录 |
| 9 | **必须写「不决定的后果，与默认」**（让对方能判断"不答会怎样"） | ❌ 不写后果，把"不表态"变成"流程卡死" |

**要求 7 的判据（把"给候选"与"编答案"的软边界变成硬判据）**：

给候选**不是**"随便想几个选项让对方挑"——那等于你在编业务语义。每个候选必须能填出来源，来源只有四类：

| 来源类型 | 写法 | 例 |
|---|---|---|
| **用户原话的派生** | `依据：用户说"太慢"` | (a) 单轮端到端延迟 |
| **既有工件的引用** | `依据：docs/plans/03-x.md:12 已声明 QPS=1000` | (b) 沿用既有负载口径 |
| **外部事实**（须先由 SupportRequest 查到） | `依据：<调研结论路径>` | (c) 按该 SDK 官方基准口径 |
| **历史记录**（既有记录/上次实测，非本轮实测） | `依据：<路径或锚点>（既有记录，可能已漂移）` | — |

  **引用历史数字必须标漂移风险**（否则会把旧数据当现行事实传下去）：写 `<数字> @ <锚点>` 并在旁注 `既有记录，可能已漂移`；**能本轮实测的不要引历史**（例如"测试是否全绿"当场跑一次比引旧记录可靠）。

**填不出来源 → 这条候选不该出现在表单里**：它要么退化成"开放问句"（那说明你还没理解到能提问的程度，回阶段 2），要么走 SupportRequest 去取事实。**判据一句话：这个候选，我是从哪儿知道的？** 答"我猜的/一般是这样的" → 删掉。

> 这条判据同时解决了子代理侧的问题：**你不需要知道"正确答案"就能提问**——你只需要说清"这些选项各自从哪来"。用户裁定的是"选哪个"，不是"你从哪知道的"。

**单轮问项的数量与分级**：

- **软上限约 10 项**：超过时按"必须一起答 / 可后置"两级分组（见下），并在表单开头写明预计轮数；**不要为了凑齐一轮而把可从属的细节塞进来**；
- **每条必须标依赖关系**：`必须一起答（缺一写不出 R）` vs `可先答也可后置（只挡最终 AC）`——前者是 R 的主干子句，后者是细化项。**主干项收齐即可切换产出形态**（发下一个表单或直接落 spec），不要让细化项拖住主干；
- **建议给出回答顺序**（哪几题先答最有价值），并注明"只拍前 N 题也能推进"——降低对方一次答完的压力。

**收敛自检（回报前必做）**：对比你**上一轮**的表单——**本轮是否消解了上一轮的问项？** 若你的会话里已经有上一轮答复，本轮表单只应包含**新的、且上一轮答复消解不了的**问项；重复问上一轮已答的题 = 说明我没消化答复。

**未答项怎么处理**：

| 上一轮的项 | 本轮怎么办 |
|---|---|
| **已答** | **不再出现**（重复问已答题 = 没消化答复）；若你对答复有异议，写进"现状小结/开放问题"**提异议**，不重列成题 |
| **问了但未被答复**（对方跳过） | **必须重列**——它没有被任何答复消解，不属"重复已答"。但**标注**：`（上轮未答，故重列）`，让对方区分"新问题"与"上次漏答" |
| **上轮答复产生的新项** | 正常列为新题（如定了绝对阈值后引出"是否分档"） |
| **被答复重塑、不再成立的旧项** | 改写而非照搬：按新信息重新组织候选与影响面 |

**这不是失败，不要道歉、不要写"很抱歉无法继续"之类**：本域的正常产出有两种——**能界定的 spec** 与 **需要对方决策的表单**。写不出表单（连候选都给不出）才是真的卡住，那说明你对问题的理解还不足以提问，应回到阶段 2 重读材料。

**SupportRequest 回报**（需要外部事实才能界定）：

```text
【需求域 SupportRequest】
- 缺口：<需要什么事实/依据>
- 建议输入条件（Useful 判据）：<什么样的调研成果就算满足我的需要——要具体到“回答哪几个问题、给出什么形态的证据”>
- 阻塞程度：<完全阻塞 / 部分阻塞（哪些问可以先答）>
```

> 你**不能自行派发调研**（子代理不能派生孙代理）。正确动作是回报 SupportRequest，由调度者派发支撑域子代理并把成果回填给你，你再继续。

> **你也不能直接问需求提出方**（没有用户通道）——你的 `Blocked：信息不足` 就是"我需要问"的表达，调度者会把它加工成一次问答再交给你（闭环见 dispatcher-orchestration §3.4.1 需求访谈）。**这不会让你重来一遍**：调度者会把答复回填到**你当前的会话**，你接着往下做。
