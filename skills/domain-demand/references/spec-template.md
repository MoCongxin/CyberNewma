# spec 章节格式（正文模板）

> **何时读**：阶段 3 落盘 spec 前读（六个章节的逐节模板与填写口径）

### 2.3 章节格式（正文模板）

```markdown
---
name: <一句话标题>
description: <一句话，必须含结论式判定条件，不是“关于 X 的规格”>
type: spec
status: draft | proposed | accepted | superseded
scope: <受控词汇>
created: YYYY-MM-DD
version: v1.0          # 可选：若项目有版本规划表则引用其版本号，不自行发明
supersedes: []         # 取代了哪些旧 spec（id 列表）
superseded_by: []      # 被哪些新 spec 取代
archs: []              # 消费本 spec 的 arch 路径（双向引用的另一半，见 §2.4）
related: []            # 相关文档（其他 spec / ontology / 设计文档）
---

# <标题>

## 一、目标谓词（Target Predicate）
<!-- 核心中的核心。必须能被写成 R(x) 并判定。 -->
- 判定对象 x = <候选对象是什么>
- R(x) = <谓词表达式，可用多行 ∧ 组合>
- 判定方式 = <怎么得到 True/False：命令 / 测量 / 人工核对清单>

## 二、范围与约束
- 范围内：<做什么>
- 约束：<硬约束，逐条编号>
- 输入：<开工需要什么>
- 输出：<产出是什么>

## 三、非目标（Non-Goals）
<!-- 显式写出“不属于本任务”的东西。这一节的作用是防止后续域自行扩范围。 -->
- <明确不做的事>（理由：<为什么不做>）

## 四、成功判据（Acceptance Criteria）
<!-- 逐条可判定、可对账。每条都应是目标谓词的一个子句或推论。 -->
- [ ] AC1：<可判定条件>｜判定方式：<命令/测量/核对>
- [ ] AC2：...

## 五、开放问题（Open Questions）
<!-- 答不上来的问题在这里，不在正文里被猜测填补。 -->
| 编号 | 问题 | 为什么它挡不住 R | 应由谁回答 | 截止时机 |
|---|---|---|---|---|
| OQ1 | ... | ... | 用户 / 上层任务 | 实施期前 |

## 六、来源与依据
- 用户原始表述：<原话摘录或会话锚点>
- 引用材料：<现有 plan / arch / memory 的 file:line 或链接>
```

**章节可按复杂度裁剪**（与设计域 arch 的轻/常规/复杂对应，不另设分档名）：

| 情形 | 裁剪 |
|---|---|
| 极简（单点替换、零星修正） | 一、四 必填；二、三 各压成一行；五 无则写“无”；六 可省 |
| 常规 | 全六节 |
| 复杂（多子系统、需拆分） | 全六节 + 在“二、范围与约束”后加 ## 二·补、子规格分解（列出本 spec 拆出的子 spec 及其 dependsOn 关系） |
